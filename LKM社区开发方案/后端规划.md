# LKM 社区 — FastAPI 后端设计方案

> 架构定位:**主体模块化单体 + 独立 AUTH 认证微服务**,基于事件驱动,预留微服务拆分边界。
> 客户端请求经 `APISIX` 接入统一限流、熔断;AUTH 用户域与主业务域走 **Apache Pulsar 统一消息总线**,以**单集群多租户命名空间**隔离(`persistent://lkm/auth` vs `persistent://lkm/biz`,见第五章)。
> 主服务内部严格分层 `api → service → repository → db/models`;AUTH 独立认证库、独立部署、独立故障域。

| Pulsar 命名空间(tenant/topic 前缀) | 覆盖域 |
|----------|--------|
| `persistent://lkm/auth/...` (命名空间 1:用户域) | AUTH 用户域(用户/认证/邮件/验证码/审计)—— 全隔离 |
| `persistent://lkm/biz/...` (命名空间 2:业务域) | 主业务域(内容/交互/通知/搜索/feed) |

> **隔离动机**:用户数据与认证协议最敏感,独立 AUTH + Pulsar 下独立命名空间形成逻辑边界隔离、最小权限、独立故障域。安全收益来自隔离与审计,而非消息产品本身;Pulsar **单集群多租户**让「用户域队列语义 + 业务域流/persistent 语义」落在同一集群的不同命名空间,较"双集群双产品"更省运维、更易隔离,并原生支持分层存储(历史事件低成本长期保留)与跨集群复制(未来多机房/灾备)。多租户/命名空间权限在 broker 侧并生效于消息级 ACL,承载最小权限隔离。

> **演进基调(重要)**:本文档是**目标蓝图**,并非对现有代码的现状描述。社区已有可运行后端 `C:\Project\LKM-Website\LKM-service`,其实际架构是 **FastAPI 单体 + SQLAlchemy async + Strawberry GraphQL + Redis 兼容缓存 + RabbitMQ(aio-pika)单总线 + APScheduler + Prefect(新引入)/APScheduler 调度 + auth 于单体内**,未落地 Pulsar(统一总线) / 独立 AUTH 微服务 / APISIX / Infisical(接入实为 nginx+astro)。现有 RabbitMQ 单总线即为向 Pulsar 统一命名空间迁移的**过渡地基**(现有 `lkm.*` 队列映射到未来的 auth/biz topic,见 §0)。**转型以现有代码为根基逐步演进**(见下节),非推倒重来。

**演进建议(以现有代码为根基)**
1. 生产切 PostgreSQL,沿用现有 Alembic 迁移。
2. **保留现有 RabbitMQ 单总线,作为向 Pulsar 统一的过渡地基**,先把现有 `lkm.*` 队列收敛到 Pulsar `persistent://lkm/auth`(用户域),业务 topic(通知/feed/索引)按判据 §6.5.4 渐进落到 `persistent://lkm/biz` —— 从最需扇出的 `notify` 拆起,而非一步全拆。
3. **AUTH 独立微服务(定案)**:把 `app/modules/auth` 收敛为强内聚模块(现有 import-linter 已约束边界,§7.2),再按 §7.5 判据搬成**独立部署的认证微服务** + 独立认证库。此为既定演进目标,时序置于 M3。
4. 调度:**APScheduler** 承担简单 cron/周期触发(已有 cron→RabbitMQ 拓扑,不迁 arq);**复杂数据管道(ETL/对账/历史重跑)演进由 Prefect(或 Dagster)编排**(DAG 依赖 + 失败重试 + 回填,运营),APScheduler 只做其简单触发入口。
5. APISIX / **Infisical(替代 Vault)** 列为后置增强,不阻塞当前。
6. **指标(Prometheus+Grafana)前移、作为 M0.5**(见 §6.2 / M0.5):承接现状 `latency_ms` 计算 + `health` 端点,尽早掌握 QPS/延迟;Sentry 保持错误追踪,OTel 链路可更后置。
7. **跨 AUTH 数据访问 =「单一在线读模型(user:snap 缓存 + API 回退)+ 报表宽表(user_dim)」**(§5.4):随 AUTH 独立服务化(第 3 条)落地 `clients/UserAPIClient`(进程内 HTTP + `user:snap` 缓存回退 + 变更即失效)作唯一在线数据源;`etl/` 周期增量同步 `user_dim` 宽表仅服务运营报表/后台列表,替代原跨域事件桥、简化双读一致性。

## 二、整体架构

**主体模块化单体 + 独立 AUTH 认证微服务**。

- **主服务**:内容/交互/通知/搜索/feed 等业务域的模块化单体,共用进程、代码严格分层;未来每个 `service` 模块即为候选微服务边界。
- **AUTH 服务**:独立部署的认证微服务,持**独立认证库**,单独故障域与扩展,为最敏感的用户域提供边界隔离(既定架构定位,立项即在主服务内收敛 auth 模块,时序 §0#3 / M3)。
- **统一消息总线(单集群多租户)**:AUTH 用户域走 **Pulsar `persistent://lkm/auth`**,主业务域走 **Pulsar `persistent://lkm/biz`**——两个**命名空间(tenant)**在**同一集群**内隔离(队列/累积语义 + 消息级 ACL),替代旧「RabbitMQ+Kafka 双集群」;现有 Rabbit 单总线只作为过渡地基。

**启动 / 就绪依赖契约(AUTH 拆出后必须定义,防止"主服务起不来"或"AUTH 故障级联")**:

> 拆出 AUTH 后,主服务运行时依赖 AUTH(验签公钥、用户数据回退、RBAC 判定)等多项外部依赖,但**这些依赖须分为"硬依赖/软依赖",且就绪判定为复合(AND)——而非单点、更非启动阻塞**:
> 1. **启动不阻塞(懒加载)**:主服务进程**启动不等待任何下游就绪**——DB/缓存/消息总线可用即可 start;对所有下游调用一律**懒加载 + 失败可降级**,缺失不 crash、不导致主服务退出。
> 2. **验签公钥可供启动时加载**:AUTH 的 JWT 验签公钥(RS256,§4.2)启动时**优先从本地启动前已注入/缓存的公钥加载**(配合 Infisical 下发 §6.5.1),或从 AUTH `/jwks` 拉取并缓存;**公钥未就绪则主服务进入"验证暂不可用"状态**,不影响进程存活,就绪探针如实上报。避免一启动就强依赖 AUTH 在线。
> 3. **复合就绪判定(必需)**:readiness = **全部硬依赖 AND 就绪**,不是只看 AUTH 单点:
>    - **硬依赖(任一缺失 → readiness 未就绪,暂不入流)**:**DB**(写路径根基)、**Dragonfly 缓存/会话/锁(L2 缓存)**、**Pulsar 消息总线**(主服务通用队列;过渡期指现有 Rabbit,拆出 AUTH 后亦含 AUTH 主动通知消费)、**AUTH**(验签 + 用户数据回退)。这四个是主服务承接业务流量的前提。
>    - **软依赖(缺失可降级,仍在 readiness 内告知但不阻塞入流)**:**OpenSearch/搜索**(可降级)、**MinIO/文件**(必要时降级)、**Infisical**(密钥已注入后就绪不依赖)。**业务域读一致性所属 Pulsar biz 命名空间不构成就绪门槛**(未拆前无关)。软依赖故障降级,不得把服务打成未就绪。
>    - **复合语义**:任一硬依赖未就绪 → readiness 未就绪、暂不入流;但 **liveness 仍只看进程存活,不因任何依赖失败而失败**(防级联重启)。
> 4. **健康/就绪语义分级 + 探针**:`/health` 做 **liveness(进程存活,零外部依赖或仅自探不死循环)**;readiness 做**复合探活(§2 · 硬依赖 AND)**用于流量调度;部署用 **startupProbe(启动期)/ readinessProbe(硬依赖复合)/ livenessProbe(自身健康)** 三分;详见 §6.4。

### 通信三种模式并存(含 GraphQL)

- **同步(REST)** —— 客户端直接请求;APISIX 把认证路由转给 AUTH 服务、业务路由转给主服务。REST 保留**所有写、流、管理、认证端点**。
- **异步(Pulsar 统一总线,双命名空间)** —— 用户域走 `persistent://lkm/auth`,业务域走 `persistent://lkm/biz`(通知、搜索索引、feed 生成),同为 Pulsar 单集群内不同租户命名空间。
- **GraphQL(只读聚合 Query,沿用现有约定)** —— 延续 `LKM-service` 现状:**只做"聚合读 / 关系读",复用 REST 的 service 读函数,不加 mutation**。适合 timeline/feed、内容评论树、用户关注关系等扇入型读取;鉴权/写/文件流保持 REST。

> **新增读端点判据(GQL vs REST)**:多资源**聚合/关系读**(一次返回聚合、评论树、关注网)→ 优先 GraphQL;单记录直查、需要精确控制缓存键或按字节精确响应 → REST。避免未来一半读散在 REST、一半在 GQL,新增读侧按此定夺。

**API 风格**:REST 版本化 `/api/v1` + GraphQL 只读聚合,`schemas/`(Pydantic)统一请求/响应模型。

**GraphQL 与 REST 版本化共处(两条并存、不打架)**:

> REST 与 GraphQL 是两套**共存**的读侧通道,共用同一批 service 读函数与数据模型(§7.2)。**两者都走「多端点版本化」**:移动端 App 版本碎片化严重,强制升级 GraphQL schema 几乎不可能,故 **GraphQL 不采用"单端点 + 语义化缓冲"方案**(`@deprecated` 保留 ≥几个周期在业务压力下守不住,单端点会演变成堆满废弃字段的大泥球),**转而采用多端点版本化**:每个版本独立端点/schema,**与 REST 对称,新旧客户端完全隔离**:

| 维度 | REST `/api/v1` | GraphQL 多端点版本化 |
|------|----------------|---------------------|
| 版本化载体 | **URL 路径版本**(`/api/v1/...`→`/api/v2/...`) | **独立端点版本**:`/graphql/v1`、`/graphql/v2`...,**每个版本完全独立的 schema + 解析器** |
| 何时升版本 | **破坏性变更** → 升 `v2`,旧版保留运行 | schema 有破坏性变化 → **开新端点 `/graphql/v(n+1)`,旧端点保留运行**;不靠 `@deprecated` 缓冲 |
| 向后兼容 | 路径内保留旧版;旧客户端不受新版本影响 | **旧端点永久保留、按原 schema 服务旧客户端**,新旧客户端各用各 schema,天然隔离、互不影响 |
| 路由 | APISIX 按 `/api/v1/**` 分流(§2) | **APISIX 按请求头(客户端版本/`X-API-Version`)把流量路由到 `/graphql/v1` 或 `/graphql/v2`** |
| 鉴权/写 | 保留(§2) | 只读聚合,不做 mutation(§2) |

**多端点版本化协议(核心:端点隔离,不演变成大泥球)**:

- **原则 1 — 版本即端点,多端点并存**:每次**破坏性变更(删字段/改类型/收缩返回/改枚举语义)**都**新建版本端点**(`/graphql/v1` → `/graphql/v2`),各端点拥有**完全独立、自洽的 schema 与解析器**;旧端点**保持运行不删除**(最小化到无新流量但持续服务存量客户端),**不往旧 schema 硬塞 `@deprecated` 废弃字段**——端点按版本隔离,避免"单端点堆废弃字段"的大泥球。
- **原则 2 — 端点只增不删(直到彻底下线)**:新端点上线后,旧端点**按实际客户端占比/迁移节奏逐步弃用**,到某版本客户端占比可忽略时再整体下线;**不被"业务紧急下线"打破**——因为新需求进新端点,旧端点稳定不侵入。
- **原则 3 — 唯一归属承袭**:同一读能力**只有一个归属**(REST 或 GQL,§2 新增读端点判据),不双写;归属 GQL 的破坏变化走**新版端点**,归属 REST 的走 REST 版本——两端点/两通道对同一数据的契约各自独立版本化,可追踪。
- **原则 4 — 兼容优先**:能不加破坏的(加字段/可选化/加枚举)直接进**当前端点**即可;只有破坏性才开新端点;**解析器复用**:各版端点的解析器共享底层 service 读函数(§7.2),仅 schema 层版本化(防过度重写)。
- **GQL 读侧约定(补 §0 差距表"需补 GraphQL 读侧约定")**:只读聚合 Query 复用 REST service 读函数;版本策略 = **多端点版本化(`/graphql/vN` 独立 schema + 解析器 + APISIX 按客户端版本路由)**,破坏开新端点、旧端点保留;schema 变更登记 changelog,**不靠单端点 `@deprecated` 缓冲堆积**。

**GraphQL 查询防护(复杂度 / 深度 / 超时,必须)**:

> GraphQL 作为聚合读,**恶意/失误客户端可构造嵌套极深的查询**造成 **N+1、资源耗尽、单请求拖垮**(聚合读尤其容易放大)。定案:
> 1. **深度限制(strawberry 扩展)**:启用 **`QueryDepthLimiter`**(如 max_depth=8~12),拒绝超深嵌套查询;防"层层 join 拉爆 DB / N+1 爆炸"。
> 2. **复杂度限制**:用 **查询复杂度评分(QueryCostLimiter/过重 field cost)**——每个 res**over 一个复杂度分上限(防单请求聚合过多字段/列表),超限直接拒绝全查询**;并可细化到"匿名/限流低配额,登录更高配额"。
> 3. **全局超时**:设置**查询级执行超时**(如 5s)与 HTTP 兜底超时,**超时即返回错误(非无限执行)**,杜绝慢查询占用 worker/DB 连接。
> 4. **与批量/DataLoader 配合**:深查询内的列表字段**必须走 DataLoader/批查询**(§5.4 批量接口的读侧复用),避免 N+1——深度/复杂度限制是"硬上限",DataLoader 是"性能底座",两者都要。
> 5. **监控**:GQL 执行时间/深度分布/被拒查询数暴露指标(§6.2),被拒激增即告警(可能被恶意探测)。

### Pulsar 命名空间职责边界(替代旧双集群总线)

| Pulsar 命名空间/租户 | 覆盖 | 典型事件 | 订阅方(消费者) |
|------|------|----------|--------|
| `persistent://lkm/auth`(用户域) | AUTH 用户域与队列语义(隔离) | 邮件验证码、审计、`user.banned`/`user.registered` | AUTH 内部消费者(邮件/审计);主服务(变更失效/主动通知) |
| `persistent://lkm/biz`(业务域) | 主业务域流 | `post.created`、`interaction.liked`、`comment.published` | 通知/搜索/feed 消费组 |

> **约定**:两个命名空间在**同一 Pulsar 集群**内多租户隔离(auth 侧可利用 Pulsar 非持久/延迟队列 + 命名空间 ACL,业务流与用户队列互不串扰),**不裸跨命名空间直连**;AUTH 内部异步(邮件/验证码/审计)在 auth 命名空间内闭环。**主服务需读 AUTH 用户数据不经过事件桥**:实时读走「`user:snap` 缓存 + API 回退」,批量/离线走 ETL 周期同步(见 §5.4)。
>
> 过渡期注:现存 Rabbit 队列(`lkm.*`)映射到 auth/biz 命名空间的目标 topic(见 §0),在 Pulsar 迁移完成前其旧语义仍在 Rabbit 上闭环。

> **单向权威边界(用户数据定案,强约束)**:
> 1. **AUTH 是用户核心操作的唯一入口与权威源**:用户/认证表(`user.py`)唯属 AUTH;凡**涉及用户核心操作的数据读写**(注册/登录/资料修改/凭据/角色权限/封禁等)一律以 **AUTH 为唯一入口与最终落库对象**,别无旁路。
> 2. **主服务绝不直接修改任何 AUTH 数据**:主服务不得对用户表做任何写操作(增删改),不得跨库 join、不得绕过 AUTH 直连其库;主服务需要用户数据**在线读走 AUTH 只读 API + `user:snap` 缓存回退,报表走 ETL 宽表**(§5.4),不依赖 `user.*` 事件桥。
> 3. **`user_dim` 宽表 = AUTH 数据只读副本(报表/后台专用)**:主服务的 `user_dim` 由 ETL 单向灌入、**完全只读**,**仅服务于需要复杂 SQL 的运营报表/后台管理列表,不作为 feed/评论等在线读的数据源**;**主服务对 `user_dim` 只有读权限,无写入/回写路径**,任何用户数据修正必须回到 AUTH 完成,严禁把 `user_dim` 当可回写的第二数据源。在线读**单一以 `user:snap` + API 回退为准**。

### 3.2 Alembic 迁移策略

- 环境配置 `alembic/` + `alembic.ini`,`revision` 自动编号,`down_revision` 链保证可回滚。
- 迁移命名语义化(`0001_init`、`0002_user_table`),**每个迁移只做一件事**。
- `autogenerate` 生成骨架后**人工审校**(索引、约束、`ON DELETE CASCADE` 等 autogenerate 不准)。
- 多环境:`dev` / `staging` / `prod` 共用脚本,`sqlalchemy.url` 走环境变量。
- 生产大表变更走分批(避免全表重建),CI 先校验,大表用 `--sql` 导入 DBA 评审。

### 3.3 Repository 模式(轻量)

业务逻辑不直接碰 SQLAlchemy,便于测试与未来换存储。

- 提供 `AsyncRepository[Model]` 泛型基类,收拢 `get/get_many/create/update/delete` 通用 CRUD。
- 业务专属查询再子类化,避免重复样板与过度抽象。

**连接与连接池(主动配置,防 PG 连接耗尽)**:

> Outbox Poller + Web 请求 + APScheduler(及 worker 消费者)**共用同一 DB 引擎时,总并发连接数需受控**,否则会打满 PG `max_connections`。定案:
> 1. **给出明确池大小基准**:asyncpg 连接池默认 `pool_size=20, max_overflow=10`(可调)。**Web/读热路径用小池 + 合理 max_overflow**,避免请求突发占满。
> 2. **不同组件独立连接池(关键)**:**Web(API 请求)**、**Worker/Poller(后台投递与消费)**、**APScheduler(周期任务/ETL)** 各自持有**独立的 Engine/连接池配置**(读少写多的 web 池、批处理池、调度池),互不挤占——**Poller/ETL 的周期突发不拖垮 Web 在线请求的连接**。用 `create_async_engine(pool_size=..., max_overflow=..., pool_recycle=...)` 分池。
> 3. **监控连接水位**:连接池空闲/占用/等待超时暴露指标(§6.2),占用接近 80% 即告警;配合上面独立分池定位是哪个组件在打满。
> 4. **拒绝崩溃**:池满时**等待/超时重试**(不禁抛 OOM);结合队列削峰(异步背压),而非无限开池。

## 四、认证、鉴权与安全(AUTH 微服务)

**认证收敛到独立 AUTH 微服务(定案)**:用户/认证表、登录、token、RBAC、OAuth 全部由 AUTH 负责,其余服务不持认证状态、不碰用户表。**AUTH 与主服务的会话状态彼此隔离**,实现边界隔离与最小权限。立项后先在主服务内收敛 `auth` 为强内聚模块(import-linter,§7.2),再抽取为**独立部署的认证微服务**(时序 §0#3 / M3)。

### 4.1 AUTH 服务边界

| 由 AUTH 处理 | 不落在 AUTH |
|--------------|-------------|
| 注册/登录/登出、发 Reset/验证码 | 内容、评论、点赞等业务逻辑 |
| Access/Refresh Token 签发、轮换、撤销 | 业务资源的所有权校验主体 |
| 角色/权限管理、封禁、`auth_version` | 帖子/评论的 `owner` 判定 |
| OAuth2/OpenID 第三方绑定 | 账号画像、关注关系 |
| 用户域异步(邮件/审计,走 RabbitMQ) | feed/搜索索引 |

- **APISIX 路由分流**:`/api/v1/auth/**`、`/api/v1/users/me` 等转发 AUTH;业务路由转主服务。
- **跨服务用户读取**:主服务不跨库 join 用户表;实时读走 AUTH 只读接口 + 本地缓存回退,批量走 ETL 宽表(§5.4),不再用事件桥。

### 4.2 JWT + Refresh Token

| Token | 存哪 | 有效期 | 用途 |
|-------|------|--------|------|
| Access Token (JWT) | 客户端内存 | 15 分钟 | 访问受保护接口 |
| Refresh Token | `HttpOnly` cookie(或 header) | 现状 7 天(可调) | 静默续期 |

- JWT 签名:**现状 HS256 对称**(共享 `jwt_secret`,代码实证);**演进目标 RS256 非对称**(拍板定案)——AUTH 独立服务化后由 AUTH 持私钥签发、主服务/网关持公钥验签、不共享私钥。**迁移时序(落地 M3)**:AUTH 改用新 **RSA 私钥签发**;主服务/网关同时配置 **HS + RS 双验签器**,按 token header/签发时间路由验签;**灰度一个 refresh 周期(≥ 现有 7 天)后关闭 HS 验签器**,期间旧 HS token 仍可验、到期自然下线,不回退。过渡期对称密钥仅用于**保守互验证权**(AUTH 自我校验),不出网。`sub` 放 user_id,`aud` 分区区分套令牌(现状 `lkm:web`/`lkm:temp`/`lkm:admin`,防 token 误用),payload 只放非敏感声明。
- 现状已具备的安全要素:**Argon2id 密码哈希**、**Refresh Token 轮换**(DB 存哈希)、**三套 audience 隔离**、**`token_version` 踢下线**(改密/登出后使旧 access 失效)。
- 登出/撤销:**定案「DB 为准、Redis 仅加速预检」**——撤销状态权威在 DB(`refresh_tokens.revoked_at`,现状即如此);Redis 仅缓存最近撤销的 `jti` 做**快速预检**(命中必拒),未命中仍回查 DB,避免 Redis 丢失时放行已撤销 token。**Refresh Token 轮换**;`auth_version` 字段可在改密/封号时一键踢下线全部会话(DB 判据)。**预检缓存同时纳入 `token_version`**:改密/封号 bump 版本后,把新的 `auth_version` 写入预检缓存,主服务先比对 token 携带的版本号,低于当前版本直接拒,避免改密后旧 access 仍持续打主服务(DB 为最终判据)。
- APISIX 可在网关层校验签名/过期,无效直接 401 不落到后端;后端经信任链/`sub` 映射当前用户(需信任 `sub` 或调用 AUTH 校验)。

### 4.3 密码与会话安全

- 密码:`argon2`(Argon2id),salt 内建于哈希串,不随机盐存库。
- 登录:限流(APISIX/Redis)+ 失败锁定。
- CSRF:Refresh Token 用 `SameSite=Lax`;API 无状态不受 CSRF 影响。

### 4.4 RBAC 权限模型

功能权限(RBAC)+ 资源级所有权两层:

- **功能权限**:`user / group / role / permission` 四表,角色如 `root / admin / moderator / member`;角色与权限**由 AUTH 管理**,主服务通过 `require_roles("admin")` 或调用 AUTH 判定。
- **资源所有权**:帖子/评论允许 `owner` 或 `moderator` 修改删除——业务侧函数级检查(如 `ensure_can_delete_post(post, current_user)`),`owner`/`moderator` 判定依赖 AUTH 的会话与角色结果。

### 4.5 中间件与防护

- `TrustedHostMiddleware` + 严格 CORS(白名单)+ HTTPS 强制(HSTS),AUTH 与主服务各自配置最小暴露面。
- `SecurityHeaders` middleware(内含 `nosniff` / `frame-ancestors` 等)。
- 全链路**输入校验(Pydantic v2)+ 输出序列化**。
- OAuth 2.0 / OpenID:在 AUTH 内用 `httpx` + 标准 OAuth2 flow,账号绑定进 AUTH 库的 `user_oauth_accounts`。

### 4.6 密钥管理(Infisical,替代 Vault)

密钥不落代码库、不落环境变量明文。AUTH 与主服务启动时**各自**从 **Infisical** 拉取 DB 密码、JWT 密钥、第三方 client secret;消息总线(目标 Pulsar,过渡 Rabbit)与 L2 缓存凭据亦经 Infisical 分发,注入应用上下文。Infisical 提供 Dashboard+SDK+CLI 与 GitOps 加密同步(dev/test/prod),较 Vault 学习与运维成本更低,可直接对接 K8s Secret 与 Docker Compose。

## 五、消息驱动:Pulsar 统一总线(auth/biz 两命名空间)

> 主业务域用 Pulsar **`persistent://lkm/biz`**,AUTH 用户域用 Pulsar **`persistent://lkm/auth`**——**单集群内两命名空间多租户隔离**(旧「Kafka+RabbitMQ 双集群」已弃用,现 Rabbit 单总线为向它过渡地基)。核心挑战仍是**数据库事务与事件的一致性**,二者皆以**事务发件箱**保障。**业务代码不直接触碰任一总线 SDK,统一经消息抽象层收发(§5.0)**——降低单集群多命名空间的运维负担,Pulsar 以分层存储支持历史事件低成本长期保留、以跨集群复制支持未来多机房/灾备与命名空间级故障隔离。

### 5.0 统一消息抽象层(统一总线之上,业务无感)

> **动机**:若业务代码直接上下手,发/收事件要懂 topic/命名空间、subscription/ack、重试/幂等,运维负担重。加**一层统一消息抽象**,让业务只发/收"逻辑事件",由抽象层路由到对应 topic。
> 1. **统一编程接口**:`core/messaging.py`(`或 events/transports`)暴露**业务无关的极简抽象**——发布 `publish(logical_event)`、订阅 `subscribe(logical_topic, handler)`,输入输出为**统一事件对象(logical topic / key / payload / event_id)**,**含序列化(Schema 兼容,§5.2)、幂等、重试钩子**。
> 2. **逻辑主题 ↔ topic 映射表(唯一维护点)**:业务声明**逻辑主题**(`post.created` 等),**映射层**把它路由到 **Pulsar topic(全名如 `persistent://lkm/biz/post.created` 或 `persistent://lkm/auth/user.updated`)**;映射表集中一处(配置或注册表)。**新增/改事件只改映射表,不动业务代码**。
> 3. **transport 可插拔,切换只改配置**:默认 **Pulsar transport**(统一产选);过渡期对存量仍在 Rabbit 的队列配 **RabbitMQ transport(现状,尽迁移时收敛)**。业务对两者用的都是同一 `publish/subscribe` 抽象,**某 topic 落后哪个命名空间由映射决定**——改传输仅改配置,业务无感。
> 4. **减少运维负担**:运维**只需维护映射表与命名空间/topic 配置(及必要的 producer subscription)**,无需各业务点分散处理总线差异;统一的重试/幂等/死信/监控(**§5.1 失败分类、§5.3 语义、§6.2 指标**)在抽象层一次落地,收口于 `outbox` + `event_failures`。
> 5. **演进无缝(∂§6.5.4)**:当某业务域(通知/索引)需被独立 scale,只需把其逻辑主题**迁到 `persistent://lkm/biz` 下的独立 topic(level-2 partition 或租户调整),业务代码零改动**——抽象层让"存量 Rabbit 起步 → Pulsar 统一"迁移是天然支点。
> 6. **约束**:抽象层只做**统一收发**,不吞总线能力差异——需要独立编排 group 的 lag、延迟/死信(TTL)语义时,在 Pulsar transport 内暴露对应 subscription/TTL/死信配置,业务按需显式选用;**auth/biz 命名空间隔离由消息层强制,不跨命名空间直达**(§2)。

### 5.1 事务发件箱:DB 与事件的一致性(所有命名空间通用)

"数据写入成功"与"事件发出"必须原子。直接"写 DB 后再发 MQ"存在窗口,会造成不一致与丢失。该模式在**所有命名空间 topic 上都适用**(持久 topic 以 outbox 表驱动投递)。

```
 ① HTTP请求 → 事务内:
    - 写入业务表(如 Post 表 / User 表)
    - 写入 OutboxEvent 表(status=pending, topic='post.created'(或 exchange/rk),
                             key=post_id/user_id, payload={完整数据})
    一起 COMMIT(原子)
 ② 独立 relay(**定案:应用内 Outbox Poller + 领导者选举**,不用 Debezium/CDC,免引入额外组件):
    领导者选举:同集群仅一个 leader 实例扫描投递,其余副本为 follower
      (DB 租约表 + 心跳 / Redis 分布式锁 TTL续约;leader 失联即被接管,自愈)
    并发安全兜底(leader 内多线程):SELECT ... FOR UPDATE SKIP LOCKED 领取:
    - 领取:leader 内 SKIP LOCKED 取未锁 pending + 标 locked_at/locked_by(提交取行)
    - 投递:发布到 Pulsar 相应命名空间 topic(如 persistent://lkm/biz/... 或 lkm/auth/...)
    - 收尾:status=published 清锁;失败保留 pending,指数退避 + next_retry_at
    - 兜底:清理超时陈旧锁(locked_at 超阈值视为崩溃,重置可领)
 ③ 各消费者(通知/搜索/feed;AUTH 邮件/审计):
    各自独立消费同一事件,按 event_id 幂等处理
```

- **原子性**:DB 与 outbox 同事务提交,要么全成要么全败。
- **不丢、可按序**:outbox 记录带 `created_at`/序列,relay 保证顺序与至少一次投递。
- **幂等**:消费者端按 `event_id` 幂等(Redis/DB 唯一约束去重),容忍至少一次语义。

**领导者选举 + 锁兜底(多副本安全,必须配套)**:

> **K8s 下隐患**:若按"多副本都常驻跑 poller、靠 `SKIP LOCKED` 打散"设计,则**每个 Pod 副本都空转轮询、重复抢 DB 锁**,滚动更新/驱逐时实例忽起忽停、锁竞争加剧;且全量类任务(全量 ETL/对账)需要"全集群唯一执行者"语义,`SKIP LOCKED` 对单条领取可行、对"整体唯一"不成立。故**用领导者选举让同一时刻只有一个 poller 在跑**:
> 1. **领导者选举(核心,应对 K8s 多副本)**:poller 作为 **Leader** 运行——**同一时刻仅一个实例持有领导权、扫描并投递 outbox**,其余副本为 follower(不轮询、不占 DB)。领导权用 **DB 租约表 + 心跳** 或已有 **Redis 分布式锁(TTL 续约)** 实现;leader 失联超租约即被接管(follower 竞争晋升),故障自愈。
> 2. **`SKIP LOCKED` 降为兜底**:leader **进程内多线程/多协程**领取时仍用 **`SELECT ... FOR UPDATE SKIP LOCKED` 防重复领取**;leader 崩溃到被接管前的窗口、或降级多 leader 场景,由它兜底防重投——**不再是"靠它把多实例打散"的主手段,而是租约之下的并发安全网**。
> 3. **一致性与幂等双保险**:即使个别事件被重复投递,消费者端按 `event_id` 幂等(§5.1)抵消;领导者选举 + `SKIP LOCKED` + 幂等三重防线,任一层失效都不会丢事件或重复结算。
> 4. **一次一事务**:领取与投递之间**不入长事务**——领取(锁+标 `locked_at`)→ 提交 → 投递 → 更新 `status=published`(或失败计数/`next_retry_at`)。避免持锁跨网络拖长事务。
> 5. **锁兜底字段**:表设 `locked_at`/`locked_by`;启动时(及周期)清理超阈值的**陈旧锁**(如>5min 视为崩溃)重置可领,配合租约接管。
> 6. **扩缩容**:需要更高吞吐时,按**领域分片**(每领域一个 leader/消费组)而非所有副本齐跑;垂直扩 leader 内 worker(≤ CPU),或按并发领取并发度扩。
> 7. **监控**:outbox `pending` 积压、leader 交接次数/选举抖动、`locked_at` 超期、投递失败计数(接入 §6.2);无 leader 或选主抖动即告警。

**outbox 表分区与清理(防"数月后扫描性能突降",必须)**:

> outbox 是**所有事件发布的必经单表**——若只涨不清理,relay 的 `SELECT pending` 扫描成本随表膨胀**线性上涨**,业务量上去后数月即性能突降。定案(**用 TimescaleDB 扩展接管时间分区与压缩,免手工分区维护**):
> 1. **转换为 hypertable(自动时间分区)**:outbox 以 `created_at` 建 **TimescaleDB hypertable**,Timescale 自动把数据切到按时间的 chunk(时间间隔可配),**省去手动 `CREATE TABLE ... PARTITION BY RANGE` + 维护分区**;relay 只扫描**最近热 chunk(近 N 天)**,历史 chunk 不再参与 pending 扫描——扫描成本恒定在有待投递的时间窗。大表带索引预警人工做 indexes。
> 2. **chunk/local 索引 + 压缩**:pending 派发依赖的索引(**`(status, next_retry_at)` 或 `(status, created_at)`**)建在 hot chunk 内压缩友好;历史 chunk 启用 **Timescale 原生压缩**(列式,压缩率 90%+),再次压低存储与扫描成本。
> 3. **扫描窗口收缩**:relay 的领取查询**始终限定时间窗**(`next_retry_at <= now + 窗口`)与**仅 status=pending/failed 重试**,已 `published` 的历史行不扫。
> 4. **数据保留与归档**:历史已消费完成的旧数据由 **Timescale 数据保留策略(DROP chunk/搬移)** 或**连续聚合/best-effort `archive` 表/冷存储**按需收,彻底移除手动分区清理;**`failed` 已进 `event_failures` 兜底表(§5.1 失败分类)的从 pending 摘除**;清理阈值(保留 N 天热数据)集中配置。
> 5. **巡检**:pending 积压仍高但实际无待投递 = chunk/保留失效,告警(§6.2);chunk 数量与保留水位纳入常规巡检(Timescale 降维实例给出健康查询)。

**失败分类与永久失败兜底(统一所有命名空间的重试语义)**:

> Pulsar(consumer 负 ack/重投 + TTL + **死信 topic**)与过渡期 Rabbit(DLX+TTL)各有重试机制,outbox 亦有自身重试,但**"永久失败"的终局处置必须统一**,否则死消息滞留、重试空转:
> 1. **失败分类**:消费者/relay 抛错时按可重试性分类——**可重试**(网络闪断、下游 429/5xx、瞬时缺资源)入各命名空间重试链;**永久失败**(schema 不符、业务校验恒失败、payload 损坏)不进入无限重试。
> 2. **兜底表**:任一主题事件超过 `max_attempts`(定案,如 5 次)仍未成功,relay/消费者将记录移入统一的 **`event_failures` 表**(status=failed、payload、error、attempt_count、首次失败时间),并从投递队列/死信摘除;**`event_failures` 周期灌入 ClickHouse 做失败模式分析(§6.2 日志分析)**。
> 3. **治理**:`event_failures` 表 + 告警(接入 §6.2)驱动人工/脚本修复后重放;成功重放即归档,避免卡死在死信 topic。
> 4. **不做无限重试**:重试链(Pulsar TTL/重投、rabbit DLX、outbox)只承担**短时抖动重试**,长时故障由兜底表接手,防止死信无限堆积掩盖真实问题。

### 5.2 命名空间主题规划:topic 全集与队列迁移映射(含 Schema Registry)

**主业务域(`persistent://lkm/biz`)** — 以业务动作命名,topic(key) = 聚合 id:

| 主题 | 内容 | 消费者 |
|------|------|--------|
| `post.*` | `post.created` `post.updated` `post.deleted` | 通知、搜索索引、feed |
| `interaction.*` | `interaction.liked` `interaction.commented` `interaction.followed` | 通知、feed、计数 |
| `content.*` | 标签/分类变更 | 搜索、feed |
| `notification.*` | 通知派发派生结果 | 日志、审计 |

- **key = 聚合 id**(如 post_id),同一实体事件有序。
- **Schema Registry** 管理协议,`post.v1` 兼容演进,新增字段不打断已有消费者。

**用户域(`persistent://lkm/auth`)** — AUTH 专用命名空间,与 `lkm/biz` 隔离。目标 topic 直接用**命名空间全名 + 语义后缀**表达事件语义(过渡期仍在现有 `lkm.events` Rabbit 交换机上按下表语义闭环,route key 沿用 `event.*`/`cron.*` 命名):

| Pulsar topic(auth 命名空间,目标) | 语义 / 内容 | 消费者 |
|------|------|--------|
| `persistent://lkm/auth/emails.*` | 邮件 verify/welcome/password_reset | AUTH 邮件 worker |
| `persistent://lkm/auth/audit.*` | login_fail/permission_change 审计 | 审计 worker |
| `persistent://lkm/auth/user.updated` | 用户变更 | 主服务**变更即失效**(仅失效 `user:snap:{id}`,§5.4/§5.6) |
| `persistent://lkm/auth/user.session_revoke`·`user.banned` | 封禁/会话下线 | 主服务变更即失效 + 业务侧封禁/下线会话 |

> **事件只做"失效/主动通知",不做缓存的"值写入"**:主服务在线读用户信息(昵称/头像)**单一走「`user:snap` 缓存 + API 回退」**(§5.4);`user_dim` 报表宽表仅由 ETL 增量维护、不需即时事件。`user.updated`/`banned`/`session_revoke` 等 AUTH **主动发起**的变更事件(主服务无法预知何时需查,API 回退不适用),用于**仅失效 `user:snap` + 触发业务动作(封禁/下线)**;因在线读单一依赖 `user:snap`,失效只此一处、无需标脏宽表,简化一致性维护。

**现有队列(send/notify/points/jobs 4 主队列 + dlq 死信)→ 规划的归属映射**(落地时必须闭环,避免丢队列):

| 现有队列(现状) | 现状消费 | 规划归域(目标 Pulsar 两命名空间) |
|------|------|------|
| `lkm.send` | 邮件/通知单发 | 用户域 → `persistent://lkm/auth`(目标;现状仍 RabbitMQ 过渡) |
| `lkm.notify` | 通知推送 | 业务域 → `persistent://lkm/biz`(目标;M4 按 §6.5.4 迁,**过渡**期先行保留于此 Queue) |
| `lkm.points` | 积分事件处理 | 业务域 → `persistent://lkm/biz`;暂留 RabbitMQ,入 Pulsar biz 时迁 |
| `lkm.jobs` | 通用任务 + cron.* 调度 | 主服务通用队列,保留(总线触发语义,过渡) |
| `lkm.dlq`(死信) | 失败人工治理重投 | 保留 DLX;TTL 自动重试为**新增**;目标形态最终以 Pulsar 死信 topic 收口 |

> **现状澄清**:现有 `lkm.dlq` 的 DLX 为 **FANOUT**,死信落 `dlq_messages` 表走**人工治理重投**,并无 TTL 自动重试。"DLX + TTL 自动重试"是**规划新增能力**,非现状——落地 M1 时先补齐该能力,再谈自动重试。

- 每个业务类型独立 queue,**死信队列(DLX)+ TTL** 兜底重试与失败分类(TTL 自动重试为新增,现状为人工 DLQ 治理);目标形态过渡到 Pulsar dead-letter topic。
- RabbitMQ 作为**过渡地基**启用 **TLS、vhost 隔离、per-user 权限、审计日志**,安全即"隔离"而非仅靠产品本身。
- **演进原则**:先让业务域从 `notify` 起步落到 **Pulsar `persistent://lkm/biz`**(M4/§6.5.4);`send/points` 待其 topic 迁到 auth/biz 命名空间留过渡**不急于一次全迁**,避免"过渡 Rabbit 与目标 Pulsar 并存迁移期"一步到位带来的断流空窗。

### 5.3 消费者语义

消费者**统一经 §5.0 抽象层订阅**(`subscribe(logical_topic, handler)`),ack/offset 等语义在 transport 内落地,业务 handler 只关心处理与抛错:

- **Pulsar transport(统一,目标)**:`persistent://lkm/biz`(业务域)/`persistent://lkm/auth`(用户域)两命名空间的 consumer;按领域分组(通知/索引/feed)独立消费进度;**手动 ack + 业务幂等完成后 ack**,失败负 ack/重投 → 死信 topic(Pulsar)。过渡期对仍在 Rabbit 的存量队列配 **RabbitMQ transport**(`aio-pika` 异步消费者,**现状,尽迁移时收敛**,§5.5 下图注)。
- **RabbitMQ transport(过渡期用户域/存量,非目标)**:`aio-pika` 异步消费者;**定案手动 ack** + 按 `event_id` 幂等去重,处理成功才 ack,失败入 DLQ 重试——仅作向 Pulsar 迁移前的过渡语义。
- 最终一致性补偿/重试由 **Pulsar 死信 topic / 过渡期 Rabbit DLX+TTL(新增,现状为人工 DLQ 治理)+ APScheduler 定时重扫**兜底(不引入 arq)。
- 各 consumer 经抽象层统一接入 §5.1 **失败分类(`event_failures` 兜底)与重试**,ack/offset/重投等差异在 transport 内收敛,一致性语义在抽象层统一。

### 5.4 跨 AUTH 数据访问:API 回退 + 缓存 + 报表宽表

用户域与业务域**用户信息读取路径不再走事件桥接**,改为**单一在线读模型 = `user:snap` 缓存 + AUTH API 回退**;`user_dim` 宽表收窄为**仅运营报表/后台列表专用**。AUTH 内部异步(邮件/验证码/审计)仍保留 RabbitMQ(§5.2 用户域),不受影响——**本小节只约束"主服务需读 AUTH 用户数据"的跨服务路径**:

```
在线读(作者昵称/头像、鉴权 sub 映射、封号状态等——feed/评论/关注网/帖子列表都走这里):
  主服务 ──读本地缓存 user:snap 命中?──▶ 直接返回
        └─未命中─▶ 进程内 HTTPClient 批量调 AUTH 只读接口 ──▶ 写回缓存 + 返回
变更即失效(确保在线读时效):
  AUTH 用户变更(user.updated / banned / session_revoke,§5.2 事件)
    ──▶ 主服务消费 ──▶ 仅失效 user:snap:{id}(删缓存,下次读回退 API 取新值)
        ──▶ 下次读到自动从 AUTH 拉新版本(带版本 CAS,防 LWW)
报表/后台管理列表(需复杂 SQL,允许分钟级滞后):
  APScheduler 周期任务 ──增量拉(updated_at>last_sync)──▶ 灌入 user_dim 只读宽表
  user_dim 只服务报表/后台查询,不作为 feed/评论展示数据源,无需即时失效
```

- **在线读 = 单一读模型「`user:snap` 缓存 + API 回退」(唯一在线数据源)**:主服务所有**面向在线用户的用户信息读取**(feed/帖子列表/评论树/关注网展示作者)一律注入 `UserAPIClient`(进程内 HTTP),先查 `user:snap` 缓存(§5.6),未命中回退 AUTH 只读接口并写回。**不在线读路径上混入 user_dim 宽表**,消除"双读机制一致性"复杂度。**跨总线"桥接消费者 + 幂等落库"的中间层被取消**,跨实时一致性由同步 API 直接保证。
- **批量回退 + singleflight(在线读不 N+1 不打爆 AUTH)**:一次多作者时**走进程内批量接口**(AUTH `GET /v1/users/by-ids?ids=...`;≤200 id 一批、分批),配合 **singleflight 请求合并**(§5.6),并发下 AUTH 调用数≈未命中 key 数而非请求数。
- **变更即失效(只失效 user:snap,单一目标)**:`user.updated`/`banned`/`session_revoke`(§5.2) 事件消费后**仅失效 `user:snap:{id}`**(删除缓存),下次读回退 API 用**版本 CAS 取新值**(§5.6 防 LWW)。因 online 读不再依赖 user_dim,**不存在"需标脏 user_dim 保持在线一致"的分布状态管理**——事件处理单一、无需双失效目标。
- **`user_dim` 收窄为报表/后台专用(允许滞后,无需即时失效)**:仅**需要复杂 SQL 查询**的场景(运营报表、后台管理列表)用 `user_dim` 只读宽表;该类查询**允许分钟级滞后**,不要求与 AUTH 实时一致→ 由 **ETL 周期增量**(`updated_at>last_sync`)+ **每日全量兜底**维护,不消耗即时失效。`user_dim` 仍是 **AUTH 数据只读副本**(§3.1 单向权威边界:读权限、无回写,修正回 AUTH);**不作为 feed/评论展示的数据源,与在线读完全解耦**。
  - **增量判据**:`user_dim` 记 `last_sync_ts`,只拉 `updated_at > last_sync_ts` 的用户,全量分页仅每日/低频兜底(防打满 AUTH 读负载)。
  - **幂等**:事件消费按 `event_id` 幂等(§5.1);同一用户变更重复到达只产生一次失效,不给 `user_dim` 造成二次脏写。
- **约束**:主服务禁止反向直连 AUTH 库;实时读一律经**批量 API + 缓存回退**(禁逐条 N+1),批量/离线经 ETL 宽表,两者互不混淆。
- **限流/熔断**:HTTP 客户端(httpx)设超时/重试/熔断(§5.3 语义),AUTH 侧对只读接口做限流(§4.3);批量接口以**减少调用次数**从源头降限流压力。

### 5.5 异步任务全景

| 场景 | 载体 | 例子 |
|------|------|------|
| 业务域实时事件、扇出、多消费者 | **Pulsar `persistent://lkm/biz`**(目标;过渡 Rabbit) | 发帖→通知+索引+feed |
| 用户域异步(邮件/验证码/审计) | **Pulsar `persistent://lkm/auth`**(目标;**现状仍 RabbitMQ,过渡**) | 验证码、欢迎邮件、登录风控 |
| 定时(cron / 周期触发) | **APScheduler**(简单触发入口,投到总线:`cron.*`,现状 Rabbit、目标 Pulsar,§5.5) | 运营日报、feed 缓存刷新 |
| 简单延迟/重试/幂等补偿 | **Pulsar TTL/死信 topic**(目标)与过渡期 **RabbitMQ DLX + TTL(新增,现状为人工 DLQ 治理)** | 邮件重试、失败补偿 |
| 复杂数据管道(ETL/对账/运营日报/回填重跑) | **Prefect(或 Dagster)flow 编排**(§5.4/§6.5.1;APScheduler 仅做其简单触发入口) | `user_dim` 增量同步、计费对账、运营日报、历史回填 |
| 批量/离线数据同步 | **Prefect flow 编排 + APScheduler 简单触发**;增量 ETL(§5.4,全量仅兜底) | 拉 `updated_at>last_sync` 的 AUTH 增量灌 `user_dim` 宽表(报表/后台用) |

> **调度决策**:现有 `LKM-service` 已用 APScheduler + RabbitMQ cron 拓扑,**定案沿用**(简单 cron/周期触发随 app lifespan 绑定、DAG 式复杂管道由 Prefect 编排),**不再评估迁 arq / 不引入 Celery**。
> **归属**:邮件/验证码等用户域异步统一走 `persistent://lkm/auth`(目标;现状仍 RabbitMQ 用户域事件,过渡),与 5.4 一致。

**调度与 FastAPI 生命周期绑定(必须,防耦合风险)**:

> APScheduler 的 scheduler 若挂在**模块顶层/请求外游离**运行,会**脱离 app 生命周期**:app 未起/已关时 scheduler 仍持有、startup 前触发、shutdown 后残留任务跑数据库关闭的调用,造成**重复调度、悬挂任务、关闭后仍执行**。正确做法是把调度器生命周期**严格并入 FastAPI lifespan**:
> 1. **随 lifespan 起停(不游离)**:scheduler 在 **`lifespan` 上下文中启动/停止**——startup 段 `scheduler.start()`,shutdown 段 `scheduler.shutdown(wait=...)`;**绝不在 import/模块顶层 start**,确保与 app 同生共死。
> 2. **`AsyncIOScheduler` 绑应用事件循环**:FastAPI 是 asyncio,lifespan 内调度用 **`AsyncIOScheduler`(后台线程跑循环)**,任务入环执行并纳入统一 `trace_id`/日志上下文(§6.2);不用阻塞型 BackgroundScheduler 抢占主循环。
> 3. **防多 worker 重复调度**:uvicorn/gunicorn **多 worker 进程各自 import 会各建一个 scheduler**,同一 cron 被多 worker 同时触发 → **重复调度**。防法(二选一):**① 独立 worker-scheduler 进程**(即 §0/技术栈的现状拓扑),调度与 API worker 隔离,天然唯一;或 **② 仅主 worker(owner)启动调度器**,其余 worker 不 start。任一方式保证**同一 cron 单实例触发**。
> 4. **优雅关闭 / 拒新任务**:shutdown 先 `pause()` 拒新触发 → `shutdown(wait=True)` 等当前作业完成或**超时强停**,避免任务悬挂、避免关闭后任务仍访问已断开的 DB/缓存(L2)。
> 5. **触发结果走总线**:cron 触发后**投 `cron.*` 到总线(目标 Pulsar;现状拓扑 RabbitMQ,过渡,§5.2)** 触发对应 flow/消费者执行——调度器本身不直跑重业务,降低生命周期耦合面。
> 6. **生命周期监控**:lifespan 起停事件记日志;调度器运行态(启用/暂停/待触发队列)暴露指标,生命周期异常(未停残余)可观测(§6.2)。

### 5.6 缓存策略(L1 本地 + L2 分布式双级)

> **缓存放取值声明**:全文所述的**分布式 L2 缓存引擎为 Dragonfly**(Redis 协议兼容、多线程高吞吐,吞吐数倍于单线程 Redis);实现细节/兼容命令(L2 pub/sub、`INCR`/`DECR` 原子、锁、分布式锁续约等)沿用 Redis 语义。缓存 / 会话 / 锁 / 限流四类职责统一封装于 `core/redis.py`(现有客户端,+ 适配层),无跨多实例一致性需求的纯进程内热读另落 **L1 本地缓存(aiocache)**(双级规则见本节下文)。

**双级结构(新增:L1 本地 + L2 分布式;目标本文所指分布式即 Dragonfly)**:

> 为规避**每次热读都回退 AUTH API / 主库/L2 的往返开销**,缓存按两层分工。**L1 = 本地 in-process(aiocache)**,适合作者快照、配置、低频变更的高频纯读项;**L2 = 分布式(Dragonfly)**,承载跨进程需共享与发失效广播的状态。规则:
> 1. **L1 优先命中**:读路径**先查 L1(aiocache 本地进程内存)**,命中即返,不吃 L2 往返;L1 未命中才回 L2(Dragonfly)→ 仍未命中才回 AUTH API/DB 填充。热读示例(`user:snap:{id}`)走 **L1 + L2 两级**:每一 worker 进程内 L1 存常驻命中的快照,跨实例一致由 L2 承载。
> 2. **TTL 分级**:L1 用**短/中 TTL(秒~分钟)**,L2 用**较长 TTL(分钟~小时)**(含下文 §防雪崩的随机扰动)。
> 3. **L1 失效经 L2 pub/sub 广播(仅需要多实例一致的失效才 pub)**:变更即失效场景(`user.updated`)、需**多实例同时命中且不得读到陈旧值**的一致项,才在 L2 pub/sub 频道广播失效;收到广播的实例**同时删本地 L1 + L2**。纯单实例或接受各进程自行过期的一致性要求低的项,不必 pub——**避免为所有命中都 pub 造成放大**。
> 4. **唯一缓存读者/写者归属**:互操作数、防 LWW/CAS、对账收敛见下文各节——**L1 只读派生加速,不具备权威,权威回退逻辑与本小节全程一致**;下述"Redis/`core/redis.py`"在分布式语境即 L2(Dragonfly),L1(aiocache)仅在声明读取侧命中,不改任何权威判定、防 LWW/CAS、对账收敛方向等既有结论。

> 下面各段所谓"缓存失效/重建/Dragonfly 回收"均以 **L2 为一致锚点、L1 为加速**;防穿透/击穿(L1/L2 均适用,singleflight 见击穿段)/雪崩随机扰动双层共用。

**缓存对象与 TTL/失效(键形态以 L2(Dragonfly)为准;标注 (L1) 者可加本地 aiocache 首级)**:

| 对象 | Key 形态 | 写 | 失效/一致性 |
|------|----------|-----|------------|
| 热读内容(帖详情) | `cache:content:{id}` | 读后写 / 事件刷新 | 短 TTL(秒级)+ `post.updated` 事件失效 |
| 互动计数(like/comment/view) | `cnt:content:{id}` | 事件异步累加 | 定期落库(见下) |
| 用户快照(昵称/头像) | `user:snap:{id}` | **读回退 API 写**(未命中回退 AUTH)+ `user.updated` 事件失效 | **强一致读模型;缓存只是加速层,权威在 AUTH API;`user.updated` 变更即失效**(§5.4 下注) |
| token 撤销**快速预检**缓存 | `jti:block:*` | 撤销时写(仅供参考);**权威在 DB `revoked_at`** | 命中必拒,未命中回查 DB;禁止因 Redis 丢失而放行 |
| feed / 时间线页 | `feed:{user}:{cursor}` | 事件刷新或惰性 | 分页键 + TTL |
| 限流计数 | `rl:{scope}:{key}` | 中间件写 | 固定窗口/令牌桶 |

**作者快照 = 强一致读模型(拆出 AUTH 后最关键的读路径)**:

> 主服务拆出 AUTH 后,业务表 `author_id` **不再跨库 join 用户表**(§3.1 数据所有权),而 feed / 帖子列表 / 评论树 / 关注网等扇入聚合都要展示作者昵称头像——**全部走 `user:snap` 缓存(单一在线读模型,§5.4)**。**一旦快照失准,就是整站作者信息漂移**,故把它定为**强一致读模型**而非普通缓存,但**权威始终在 AUTH API,缓存只是加速层**:
> 1. **写入(填充)**:`user:snap` **未命中时读路径回退 AUTH 只读接口并写回**——feed/列表等一次多作者时**走进程内批量接口一次性回退未命中子集**(§5.4,禁逐条 N+1,+ singleflight);不存在/已删用户的 id 写**空值缓存**(短 TTL,§5.6 防穿透)避免反复穿透 AUTH。**`user.*` 事件不负责"写值",只负责"失效"(见 2 失效);user_dim 报表宽表不参与在线读。**
> 2. **失效(变更即失效,单一目标)**:`user.updated`/`banned` 等 AUTH 变更事件(§5.2)**仅失效 `user:snap:{id}`**(删缓存,下次读回退 API 取新值)。**在线读只依赖 user:snap,无需同时失效 user_dim**——单一失效目标,消除双状态管理。**这是"读正确性可不依赖缓存、但时效性依赖失效"的关键——变更后不再读到陈旧快照。**
> 2b. **防 last-writer-wins(缓存回填 vs 失效的竞态,必须)**:「回退填充」与「变更即失效」并发时存在 LWW 竞态——失效刚删 key,一个进行中的回退写又把**旧值填回**,旧版本后写覆盖失效。防法:**写 `user:snap` 时携带 AUTH 数据版本(如 `updated_at`)并做 CAS/版本守卫**,只允许**更新版本(>当前)`写赢`,旧版本写入被拒**;失效配合清版本/递增代数——这样无论回退写与失效谁后发生,残留缓存永远是**较新版本**,不会出现"旧数据顶掉失效"的 LWW。多进程对同一 key 的写入也因版本 CAS 收敛到最新。
> 3. **一致性保障**:在线读以 AUTH API 为准;**`user:snap` 变更即失效(删缓存 → 回退 API 用版本 CAS 取新)保证时效**,缓存短暂滞后属可接受瞬时不一致;报表 `user_dim` 允许分钟级滞后、独立由 ETL 维护,与在线读互不相混。
> 4. **验收锚点**(M3):因 `user:snap` 是按需回退的子集缓存,**不以全量 AUTH 库为 diff 目标**;正确口径是——对**已被缓存命中的每个 user_id**,抽验其 `user:snap` 值与 AUTH API 返回**一致(差异为 0)**;**用户变更(AUTH 发 `user.updated`)后 `user:snap` 在事件后失效、下次读到新版本**;报表路径走 `user_dim` 与在线读隔离。从机制上杜绝整站作者漂移与陈旧快照。
> 5. 禁止把快照当"最终一致临时兜底"对待——它是**业务读的最高频依赖**,缓存命中率关乎 QPS(§6.2 指标 / M0.5),但**正确性不依赖缓存**(回退 API)。

**通用防 LWW(所有"读后写/惰性回填"缓存的标准约束)**:

> 不只是 `user:snap`,凡"读后写/惰性回填 + 事件/变更失效"并存的缓存(如 `cache:content:{id}`、feed 页)都有同款 LWW 竞态:失效删 key 后,进行中的回填写把**旧值**顶回。统一规则:
> 1. **写缓存携带来源版本**(源的 `updated_at`/版本号 / 别名),写入用 **CAS/比较写(compare-and-set / Lua 原子比较)**:**仅当新版本 > 当前缓存版本才写入**,旧版本覆盖一律被拒——不依赖"谁先到"而依赖"谁更新"。
> 2. **失效与版本配合**:失效即移除 key 并使版本缺失;回填写只在"缓存缺版本 或 新版本更优"时落子——被旧回填顶掉的窗口通过版本守卫收敛,读侧命中即最新。
> 3. **代价取舍**:纯热点可维持**退化键名 + 版本**(值带版本号),或在 key 内嵌版本;无版本来源的缓存(如纯计数 `INCR`,见计数小节)用**增量原子操作**而非整值回填规避 LWW。

**计数读写方向(单向落库,承接 §3.1)**:
1. 写操作(点赞/评论)只写 **Redis 计数**(读加速),**DB 冗余列是唯一事实源与最终落库对象**(§3.1)。
2. 用 `INCR` 瞬时累加 + 定期批处理/事件落库冗余列(`like_count` 等,§3.1 / §5.2 `interaction.*`)。**落库必须用「增量」单向累积,严禁「读 Redis 当前全量值 → 回写 DB 冗余列」的整值覆盖。**
3. 读路径优先 Redis;**写方向必须单向**:由互动事务改 DB 冗余列(或由异步把 Redis 增量**单向**汇总进 DB),**绝不反向"以 DB 覆盖 Redis 或用 Redis 反灌 DB"双向互写**——单向是防对账死循环的前提(见下)。

**防 last-writer-wins(LWW)——计数累加的关键约束(必须)**:

> 点赞/取消点赞是**多条并发增量**,若落库走"读当前值→回写"整值覆盖,两个并发写者在不同时刻把各自看到的 Redis 旧值写回 DB,后写者覆盖先写者 → **丢一次计数 = LWW**。防法:
> 1. **增量累积,不整值覆盖**:DB 冗余列更新一律以**互动事件的核心增量/差值**单向累加(`like_count += 本次增删的净增量`),或对账时以**事实源计数**整值重建;**禁止"读 Redis 现值 → 整体回写 DB"**(读-改-写非原子,并发下必 LWW)。
> 2. **Redis 侧`INCR/DECR 天然原子**保证单次累加不错,但"落库到 DB"必须沿**单向增量通道**,Redis 与 DB 之间不做并发整值互灌。
> 3. 若某流程必须写整值(如对账重建),用**幂等重建**(§5.6 对账第 6 条)与事实源(DB 冗余列/事件累计)对齐,且**加 CAS/版本守卫**只允许按序覆盖,阻断旧值后写覆盖新值。

**对账与收敛(定案;核心目标是不死循环、必收敛)**:
0. **权威源 = DB 冗余列本身**(不建 `interaction_events` 累计表):计数的事实基准是 `content` 表上的 `like_count/comment_count` 等冗余列,Redis 仅为读加速的派生缓存。**不维护独立事件累计表作为影子权威源。**
1. **单向写方向(防死循环第一原则)**:计数只存在**一条权威写流**——互动写操作落在 DB 冗余列(同事务或单向异步汇总);**对账固定以「DB → Redis」单向回灌**,Redis 永不反向写回 DB。**杜绝"对账写 Redis → 写路径又用 Redis 反写 DB → 对账再改"的往返震荡**(这会让两边互相覆盖、永不收敛)。Redis 缓存失效/重建一律从 DB 读。
2. **对账载体**:复用 APScheduler 定时增量对账(§5.5),对账任务独立队列(`cron.reconcile.counts`),不阻塞主链路。
3. **收敛终止条件(防死循环第二原则)**:对账以 **「本轮 diff 归零(或低于阈值)」作为完成标志**;对完的 key 记录 `last_reconciled_at`,下一轮只扫 `updated_at > last_reconciled_at` 或 diff≠0 的 key,**不重复对已收敛批**,避免对账自身空转。对账写回 DB;若对账重建会改变表的 `updated_at`,则用**不触发计数组件/对账来源标记**的方式更新,防止"对账 → 变更事件 → 再触发对账"的因果闭环。
4. **判据(以 DB 冗余列为准)**:逐个 content_id,以 **DB 冗余列当前值**为真值基准,校验 Redis 对应计数是否一致;发现 drift 则以 DB 冗余列值回灌 Redis(dB→Redis 单向)。**DB 冗余列为来源与兜底,绝不反过来被 Redis 覆盖。**
5. **频度与范围**:增量对账(近 N 分钟变更且未收敛的 id)高频(秒级)收敛 Redis 与 DB 的短期不一致;全量对账低频(日级)兜底异常;一键 `trigger` 重灌单个 id 的 Redis 缓存用于运营人工修正。
6. **幂等/防重放**:对账重建 Redis 不产生新的互动事件(或不触发重复计数累加),multi-key 幂等,重复执行结果不变——保证**重复跑对账收敛到同一终态,而非越跑越偏**(防死循环第三原则)。
7. **监控与熔断**:对账 diff 率超阈值告警(暴露 Redis 与 DB 计数漂移,接入 §6.2);**若同一批 key 多轮 diff 不降反升,判定"对账震荡/死循环",暂停该 key 对账并告警**,交由人工核查单向写方向是否被破坏。

> 目的:让"写 Redis → 异步落库"的短期不一致有**定时收敛**兜底,而不是无限期漂移,也**不是震荡/死循环**。三大防死循环原则:**① 单向写方向(DB 为源,Redis 只读派生,不互写) ② 收敛终止条件(diff 归零即停、按记录增量扫) ③ 幂等防重放(重复执行收敛到同一终态)**。

**穿透 / 击穿 / 雪崩防护(均为硬性要求)**:
- **穿透(空值缓存)**:对"合法但查无结果"的 key,**显式缓存空值**(占位标记,如 `user:snap:{id}=NULL` 或 `cache:content:{id}=∅`)加**短 TTL**(秒级,远短于正常 TTL),避免不存在 id 反复穿透打 AUTH API/DB;**非法/不可枚举 key 用布隆过滤器挡非法形态**(白名单式拦截,与空值缓存互补)。
- **击穿(singleflight/请求合并,必须)**:热点 key 缓存失效时,**同一时刻多个并发请求对同一 key/同一批(如 user:snap 大批同批失效)会同时回退上游 → 瞬间打死 AUTH/DB**。防法:**singleflight(请求合并)模式**——同一进程内多个并发拉同一个 `user_id` 只放**一个真正去调 AUTH**,其余请求**复用它返回的结果**(`async_singleflight`/`@async.cached` 合并,含 L1 命中合并);跨进程再叠 **L2(Dragonfly/兼容)互斥锁重建(double-check)**,只有拿到锁的实例回填、其余等锁后读缓存,避免多实例重复回填。落点是 **§5.4 进程内批量接口 + 本 singleflight**:批量拉未命中子集 + 批内去重合并,保证并发下 AUTH 调用数≈key 数而非请求数。
- **雪崩(TTL 随机扰动,必须)**:**所有带 TTL 的缓存对象在设置过期时,对基准 TTL 施加随机扰动**(如 `TTL = base × (0.7 ~ 1.3)` 或 `base + random(0, 300s)`),避免同一批 key 同时写入、同时过期引发雪崩;扰动在写入时计算一次,单个 key 生命周期内不漂移。批量缓存(ETL 重灌、作者快照回填)也按此对**整批做 per-key 随机化**;降级一律走 AUTH API / DB。

> 现有 `core/{redis,redis_limiter,throttle}` 已覆盖客户端/限流/令牌桶(其客户端即对 L2 Dragonfly(Redis 协议兼容)的连接),按此策略在之上加 L1(aiocache)首级扩展热缓存即可,不必重写底层。

### 5.7 WebSocket 实时层

**现状(已有)**:`app/ws/{broker,manager,router}.py`,`/ws` 连接,基于 **L2 缓存 pub/sub(现状 Redis 协议广播,`ws:*` 前缀)**做连接管理与跨实例事件推送(manager + broker 处理 `ws:upload:*` 频道)。

**关键约束(L1/L2)**:ws 连接状态与跨 worker 广播**不可落 L1(进程内)**——任何需要**跨进程/跨实例**送达的新推送必须走 **L2(Dragonfly/兼容)pub/sub**(连接只能在本 worker 进程内管理,L1 无法跨实例可见)。仅"单 worker 进程内自产自消"的瞬时状态可放 L1。

**规划演进 — 建立统一的实时推层**(连接状态归 L2 发布订阅,不强耦合业务):

| 能力 | 方案 |
|------|------|
| 连接管理 | 现有 `ConnectionManager`(按 user_id 注册/注销)扩展为多线程安全容器。映射为**本 worker 进程内状态,可存 L1**(仅用于"本进程收到 L2 指派后本地下发",不承担跨实例广播) |
| 推送通道 | `ws:{user_id}:*` L2 pub/sub 频道;跨 worker 广播 **必须走 L2(Dragonfly/兼容,现状 Redis 协议已如此)** |
| 实时通知 | 业务侧触发 `notification` 事件 → worker 推送(经 L2 pub/sub)到在线连接;离线走轮询/站内信 |
| 上传进度 | 沿用 `ws:upload:{uploader_id}` L2 频道(现状),加状态事件 |
| 频道隔离 | 每人独立频道,权限校验在订阅侧 |
| 断线重连 | 心跳(application ping/pong)+ 重连 token 续期 |

**原则**:
- WebSocket 只做**推送**与**通知**,不做业务写入/强一致事务(写入仍走 REST)。
- 推送内容一律 `JSON` + `version`/`event_id`,客户端幂等去重(与 §5.1 幂等语义一致)。
- 大规模在线后再评估是否引入更重框架;当前 **L2 pub/sub(Dragonfly/兼容)** 够用。

> 现有已具备 `ws/` 基础,本章为将其纳入统一实时策略,而非新造轮子。

## 六、工程实践:错误处理、可观察性、文件存储与部署

### 6.1 错误处理协定

统一异常结构 + 错误码 + HTTP 映射,所有 service/API 抛出 `AppError`(业务异常)而非裸 HTTPException,由全局 handler 收敛。

```
统一响应(成功): { code: 0, data, message, request_id }
统一响应(失败): { code: <业务错误码>, data: null, message, request_id }
```

| 约定 | 说明 |
|------|------|
| 业务错误 | `AppError(code, message, http_status)`;错误码语义化(`AUTH_*`/`CONTENT_*`/`INTERACTION_*`),映射统一 HTTP 状态 |
| 兜底错误 | `500` + 不泄露内部堆栈(日志记录堆栈,响应不暴露) |
| 数据库冲突 | 唯一约束/`IntegrityError` → `409`:语义化(如 `EMAIL_TAKEN`、`DUPLICATE_LIKE`) |
| 乐观锁 | 复用现有版本冲突语义(文档 `VERSION_CONFLICT`),业务表冲突同样给出 `409 + 当前值` |
| 校验错误 | FastAPI/Pydantic `422`,统一格式,前端可解析 |
| 认证/授权 | `401` / `403`,错误码区分(`TOKEN_EXPIRED` / `INSUFFICIENT_ROLE`) |
| 幂等/重试 | `409 / 429` 带重试语义,consumer 侧区分"可重试/永久失败";永久失败入 `event_failures` 兜底表(§5.1),不无限重试 |
| 日志挂钩 | 每个异常经全局 handler 落结构化日志 + 关键错误上报(接入 §6.2 可观察性) |

> 现有已有 `core/err.py`、`core/common.py(ApiResp)`、`core/err(统一异常)`,规划据此标准化错误码命名与全局 handler,不必推倒。

### 6.2 可观察性

| 维度 | 技术 | 细节 |
|------|------|------|
| 错误追踪 | **Sentry(现状已接入 `core/apm.py`,保留)** | 异常捕获/告警;与指标/链路互补,非二选一 |
| 日志 | Python `logging` 结构化 JSON | 统一 `trace_id` / `correlation_id`;走 stdout,vector/fluentd 采集 |
| 指标 | Prometheus + `prometheus-fastapi-instrumentator` | 延迟/错误率/RPS;业务指标(发帖量、outbox 积压、消息总线(Pulsar)积压/lag);Grafana |
| 链路(Metrics+Traces 一体化) | **OpenTelemetry → SigNoz**(OTel 原生:链路 + 指标 + 日志一体化,替代原分散 Jaeger/Tempo+另拼 Grafana 的链路侧) | `trace_id` 贯穿 HTTP + Pulsar auth/biz 命名空间消息 + APScheduler/Prefect 任务;`contextvars` + 自动埋点 |
| 日志分析(采集→存储→检索) | **ClickHouse**(日志存储/分析;含 §5.1 `event_failures` 失败模式、行为审计周期性灌入分析) | 采集 vector/fluentd → ClickHouse;SQL 检索/聚合 UI |
| 事务/时序扩展 | **TimescaleDB 连续聚合**(§3.1)可选用于计数/度量/运营指标聚合 | M0.5 业务指标平滑聚合、行为/审计留存分析 |

> **统一口径**:错误追踪用 **Sentry**(现状),指标用 **Prometheus+Grafana**,链路+指标用 **OTel→SigNoz**,日志存储分析用 **ClickHouse**;各司其职并行互补(链路侧不再分开 Jaeger/Tempo + 额外 Grafana)。

**日志增强:add / catch / 彩色(在标准库 logging 上做等价,不引入 loguru)**

沿用 `core/logging.py`(JSON + request_id + stderr)为标准,**补三项开发者体验/健壮性特性**,全部在标准库 `logging` 上实现等价物,**不引 loguru**(避免第二套日志体系破坏现有统一):

| loguru 特性 | 标准库等价实现 | 落地方式 |
|------------|----------------|---------|
| `logger.add` | 现有 `addHandler`(幂等挂 handler,已具备) | 扩展为**多 sink**;dev 挂终端 handler、prod 挂 JSON handler 到 stderr,按 `setup_logging(level)` 区分 |
| `logger.catch` | 自定义**异常装饰器/上下文管理器** `@log_exceptions` | 包裹边界函数(consumer handler、APScheduler 任务、service 入口),自动记 `exc_info`+结构化字段并可选 re-raise,省去散落 `except: logger.exception` |
| **彩色输出** | **仅限本地开发终端** | dev 环境用 Rich(或 ANSI)的 handler 上色级别/路径;生产仍输出**无色 JSON** 交给采集——**避免彩色破坏 JSON 解析** |

- **约束**:彩色只在 `env dev` 生效(经 `settings.env` 判定),生产始终无色 JSON;`logger.catch` 不等价于多余的兜底——仍遵循错误处理(§6.1)统一收敛,仅做结构化的便捷封装。
- **不进生产路径**:这三项属于"开发者体验 + 健壮性",不改变生产 JSON 输出;生产侧真正的空档是**采集管道**(下段)。

**日志采集管道(尚未落地,列为此节主线)**:格式已具备(JSON+stderr),但**采集→存储→检索**仍空白。目标:容器 stdout/stderr → vector/fluentd → **ClickHouse(日志存储与语义分析;周期灌入 `event_failures` 失败模式、行为审计项,§5.1)→ 检索/聚合 UI**。见 §6.2 后续演进与里程碑 M5。

**指标(Prometheus)前移决策**:社区平台需尽早掌握 QPS/延迟/错误率,故**指标采集前移、早于 M5**,承接现状已有的埋点能力——`app/main.py` 的 HTTP `latency_ms` 计算、`health` 模块的 `/health`(含 db/redis/复合依赖探活,属 **readiness** 侧,与 §2 liveness 零外部依赖分级一致)即可作为 `/metrics` 的天然挂点。落地:
- 依赖加 `prometheus-fastapi-instrumentator`(自动埋点 HTTP)+ 在 `health` 路由同层暴露 `/metrics`(text 格式)
- 补业务指标:发帖量、`outbox` 积压、消息总线(Pulsar topic/lag 或过渡 Rabbit 队列深度)、投递失败计数(接入 §5)
- `Grafana` 建仪表盘:QPS、P50/P95/P99 延迟、错误率、队列堆积
- Sentry 保持**错误追踪**角色不变(与指标并列,非替代)

> 相对演进优先级:M0(基座)→ **指标前移(Prometheus+Grafana)** → OTel 链路(可更后置)。

**统一 ID**:入站请求生成 `trace_id`,传递到 Pulsar auth/biz 消息 header 与 APScheduler/Prefect 任务,全链路可串查(SigNoz)。

### 6.3 文件与媒体存储

- 图床/头像/附件 → **统一 S3 兼容对象存储抽象**,不落业务磁盘。**同时支持 MinIO / AWS S3 / 阿里云 OSS / 腾讯云 COS 等。**

**统一存储抽象与供应商切换(定案:切换只改 endpoint + 密钥,代码零改动)**:

> MinIO / S3 / OSS / COS 均暴露 **S3 兼容 API**,差异只在 endpoint、签名 region、寻址模式(path-style / virtual-host)与个别 SDK 参数。据此建**一层存储抽象**,让供应商可插拔、切换只改配置:
> 1. **统一存储客户端**:`clients/storage.py`(`或 core/storage`)封装**泛型 S3 兼容 SDK**(如 `boto3`/`aioboto3` 或等价 S3 兼容客户端),业务代码只依赖**抽象接口**(`put_object`/`get_object`/`presigned_url`/`delete_object`),**不 import 任何供应商专有 SDK、不感知具体品牌**。
> 2. **全部可配置 + 绝对不作硬编码**:endpoint、`access_key`、`secret_key`、`region`、`bucket`、(寻址模式 `addressing_style` 等)一律来自 `Settings`/密钥管理 Infisical(§6.5.1),**不写死在代码**。
> 3. **切换流程 = 改配置**:MinIO→S3/OSS/COS 或反之,**只改 `endpoint` + `access_key/secret_key`(+ 必要时 region / addressing_style)**,重启/热加载即切;**业务代码、上传/下载/预签名逻辑零改动**。
> 4. **兼容差异由配置吸收**:OSS/COS 多用 **virtual-host 寻址 + 不同 endpoint**,S3 常用 path-style;这些差异在配置层(寻址模式/endpoint override)统一吸收,抽象层内部对齐,对外行为一致。
> 5. **能力不因供应商而异**:预签名直传、对象读写、bucket 管理在各供应商以统一语义暴露;仅当某供应商不支持某能力(如特殊强制读/省区)才在抽象层做特性探测与降级,而非散落业务代码。

**文件流程(沿用现状 + 抽象化)**:
- **预签名 URL 直传**(供应商无关):客户端拿预签名 URL 直传 → 后端收事件记录元数据入库 → 经事件总线(Pulsar `persistent://lkm/biz`,过渡 Rabbit)触发缩图/审核。
- 缩略图/压缩:异步消费者处理(§5),按统一 key 后缀产出多规格。
- **MinIO 为自托管默认实现**,可无缝切 AWS S3 / 阿里云 OSS / 腾讯云 COS / 其他 S3 兼容。

### 6.4 部署与工程化

- 多阶段 Dockerfile;`uvicorn`/`gunicorn` worker 数按 CPU;Pulsar 各订阅消费者与(演进后)Prefect worker/`etl`(user_dim 增量等)作为独立进程/独立 Pod。
- **探针与启动顺序(k8s/K8s,呼应 §2 启动依赖契约)**:AUTH 与主服务**各自独立启动、无强先后依赖**;主服务用 **startupProbe(启动期,放宽)→ readinessProbe(复合硬依赖:DB / L2 缓存(缓存引擎,§5.6)/ 消息总线(Pulsar 或过渡 Rabbit)/ AUTH 全部就绪才接业务流量,§2 第 3 条) → livenessProbe(自身健康,不含任何外部依赖)**。AUTH 或任一硬依赖未就绪只让主服务 readiness 不通过(暂不入流),**不触发 liveness 失败/重启**——避免任何下游故障级联重启主服务。**软依赖(搜索/MinIO 等)降级不影响 readiness**。AUTH 先起满(作为数据源)再放主服务流量为**推荐顺序**,但不强制阻塞。
- 配置:统一收口于 `core/config.py` 的 Pydantic `Settings`(详见 §6.5);敏感项经 **Infisical(替代 Vault)** 注入。
- **Prefect 编排落地(§6.5.1 演进产物)**:复杂数据管道(`etl` user_dim 增量同步、对账、运营日报、回填重跑)由 Prefect flow 承接——DAG 依赖、失败重试、任务 UI 状态清晰;APScheduler 仅承担简单 cron/周期触发并经总线(cron.*)触发 flow,不再手写复杂重跑逻辑。
- CI/CD:测试 → lint(ruff)→ 类型(`uv run ty check`)→ 迁移校验 → 构建镜像 → 部署。
- 测试:
  - 单元:service/repository 逻辑,pytest + `TestClient`
  - 属性(property-based):**hypothesis** 对 outbox 幂等/并发边界、对账收敛防死循环自动生成用例,**不改变现有 pytest 结构与其余测试**。
  - 集成:Testcontainers 起 **PostgreSQL + L2 缓存(Dragonfly/Redis 协议兼容镜像)+ Pulsar(官方 `apachepulsar/pulsar` 镜像)** 跑真实事务发件箱、auth/biz 命名空间事件流(过渡期可选加 Rabbit 镜像跑存量队列)。
  - 契约:Schema Registry 校验事件协议
  - **序列化(读热路径)**:高 QPS Feed/Timeline 读路径以 **msgspec 序列化**(§6.5.2 读热段)为性能基底;Pydantic v2 仍负责请求/响应校验。基准测试核对 msgspec 收益后再扩读模型使用面。

#### 6.5.2 多源读聚合策略(timeline/feed 热点)

`timeline` 是 6 源聚合 + 审核过滤的扇入热点,避免每次实时全量 join:

| 手段 | 说明 |
|------|------|
| 物化视图 / 读模型 | 预聚合时间线表,事件(§5)异步刷新,读路径只查聚合表 |
| 分页游标 | 基于 `created_at + id` 游标,避免深分页 offet |
| L2 读缓存(§5.6 Dragonfly/Redis 兼容) | §5.6 `feed:{user}:{cursor}` 缓存页(L1 aiocache 首级),事件失效 |
| GraphQL 聚合读 | 现有只读 Query 贴合扇入,减少往返 |

> 先从「物化/读模型 + 游标」做起,最直接降扇入成本。
>
> **读热路径序列化**:timeline/feed 为超高 QPS 扇入读,列表响应在 Pydantic v2 校验后,出端口以 **msgspec** 序列化(`to_camel`)+ 预组装的 projection,降低多字段列表的 CPU;"校验仍 Pydantic、序列化 msgspec"分工(见 §1 序列化行)。

#### 6.5.3 搜索演进展开

| 阶段 | 方案 | 中文分词 | 同步方式 |

| P2 | **Meilisearch**(中文友好、轻量) | 内置中文分词 | 事件总线消费者(`persistent://lkm/biz` `content.*`,§5;过渡 Rabbit)同步索引 or Push |
| P3 | **OpenSearch**(大规模、聚合) | 分析器(ik/结巴) | 事件总线消费者(`persistent://lkm/biz`,§5) |

- 索引文档结构:id、title、excerpt、content、tags、author、published_at、board 等。
- 近实时:业务事件(§5 `content.*`)驱动**增量索引**;全量重建走 Prefect flow(经 APScheduler/cron 简单触发入口)、整库可回填由其 DAG 编排。
- 演进依据:量级 + 中文检索质量;P1 够了就别提前上 Meilisearch/OpenSearch。

#### 6.5.4 Pulsar `lkm/biz` 命名空间判据(何时值得把业务 topic 从过渡 Rabbit 落到 Pulsar biz)

> 演进题头强调"不阻塞",故业务域切 Pulsar `persistent://lkm/biz` 需明确触发条件,避免为引入而引入(命名空间映射/队列归属口径见 §5.2)。

| 判据 | 触发阈值 |
|------|---------|
| 扇出数 | 单事件被 2+ 独立消费者、且需求差异大(通知/索引/feed) |
| 吞吐 / 削峰 | 峰值写入超过渡 Rabbit 舒适区间,或需不同消费者独立加速(利用其分区/累积语义) |
| 重放/审计 | 需要事件重放、批处理、统一 lag 监控 |
| 失效隔离 | 某消费者(如索引)故障不应阻塞其余;订阅独立负 ack/重试/死信 |

> 未达阈值时,现有 RabbitMQ 单总线(过渡地基)+ 死信即可覆盖;达阈值再从 `notify` 起步把业务 topic 落到 `persistent://lkm/biz`(§0 演进第 2 条),用户域落 `persistent://lkm/auth`。判据触发前业务代码零改动,仅改配置映射(§5.0/§5.2)即可切换总线。

## 七、模块化设计

### 7.1 模块划分原则

按**业务领域 + 聚合根**切,不按技术层切。每个模块是**候选微服务**。

> **核心:模块边界 = 聚合根边界(DDD)**。强一致、同事务的实体属于**同一个聚合/模块**,通过同一 `Repository`/`Service` 管理、内部事务;外部关注点(独立生命周期的读者)一律**事件解耦**。**如果两个模块频繁需要"同一 DB 事务",说明它们本质上是一个聚合,不应拆成两个模块**——否则"候选微服务"与"同库强一致"自相矛盾,且每次同库事务都制造跨模块耦合、阻碍未来拆分。
>
> **模块 A 不能直接 import / 访问模块 B 的 repository 或 service。**
> 模块间只通过两种方式交互:
> 1. **同步**:调用 B 暴露的 service/接口方法(而非直接 DB 表)
> 2. **异步**:发序列事件(目标域分走 `persistent://lkm/biz`(业务域)与 `persistent://lkm/auth`(用户域),见 §5.0;**§7.1/此前"业务域走 Kafka、用户域走 RabbitMQ"为过渡/旧口径**)**由接收模块经统一抽象层消费**。
>
> **跨模块一律最终一致**:聚合之间**只经事件/接口通信,不共用强一致事务**——强一致只存在于**单聚合内部模块**。
> 如此,未来把某模块拆成独立服务时,只需把 A→B 的调用改走 HTTP/gRPC 或保持事件流。

> 过渡注:现有架构下异步事件经 RabbitMQ 单总线闭环(过渡地基,§0),其 `lkm.*` 队列按映射收敛到 Pulsar 两命名空间(§6.5.4/M4)。

> 注:上文§7.1「业务域走 Kafka、用户域走 RabbitMQ」为**过渡/旧口径**;目标统一为 Pulsar 两命名空间(`lkm/biz` / `lkm/auth`),见 §5.0。

### 7.3 依赖方向

主服务内依赖只允许朝一个"图层"方向,避免循环:

```
api (入口/路由)  →  services  →  repositories →  db/models
        ↘           ↙
        events (发件箱 → 总线)
```

**横向模块依赖**强制走事件或显式接口注入,不做直接 DB 跨表访问。**跨服务(主服务 ↔ AUTH)**实时读走 API + 缓存回退、批量走 ETL,主动通知走事件(§5.4),**禁止跨库直连**。

> **`events` 的层次定位**:`events`(发件箱 relay / 总线 producer+consumer(目标 Pulsar auth/biz,抽象层) / AUTH 主动通知消费)是**横切基础设施**,不归属任一业务层——它依赖 `db/models`(读 outbox 表)、被 `services`(写事件)与 `api`(trigger)双向调用,因此**不违反**单向分层。import-linter 规则须把它定义为横切模块(可依赖 db,但不反向依赖具体模块的 service),避免误报循环。**跨 AUTH 用户数据读不走 events,由 `clients`(API+缓存)承担(§5.4)。**

### 7.4 模块/服务间通信细则

| 场景 | 手段 | 例子 |
|------|------|------|
| 主服务模块 B 需 A 的**实时写结果** | **事件**(业务域 Pulsar `persistent://lkm/biz`) | `content` 发 `post.created` → `search` 建索引 |
| 主服务模块 B 需 A 的**数据查询** | 注入 A 的 `service` 接口 | `interaction` 查内容元数据 |
| 主服务需**用户信息** | **在线:`user:snap` 缓存 + API 回退**(单一读模型);报表:`user_dim` ETL 宽表(§5.4) | feed 显示作者昵称/头像(禁跨库 join) |
| AUTH 主动通知业务侧 | **事件**(Pulsar `persistent://lkm/auth`;现状仍 RabbitMQ,过渡→主服务,**仅主动推送类**) | `user.banned`/`user.session_revoke` → 封禁/会话下线(主服务无法预知,API 回退不适用) |
| **单聚合内部**强一致 | 聚合内部**同一 Repository/Service、同一 DB 事务**(不跨模块) | 内容聚合内发帖(Post)、点赞(Like)、评论(Comment)同事务、同模块 |
| 跨模块**最终一致** | 事件 + 幂等消费 | 内容聚合发 `post.created`/`interaction.liked` → 通知、搜索索引、feed(外部关注点) |

> **强一致不跨模块(聚合根原则)**:需要同一 DB 事务的实体**本就是同一聚合/模块**,将其在同一事务内管理;跨模块之间**一律最终一致(事件/接口)**,不存在"两个模块共用强一致事务"——看到需同事务就并入一个模块,而非跨模块硬凑。

### 7.5 "拆出去"的边界条件

把一个模块从单体拆成独立服务,或判断一个服务是否已解耦,需满足:

- [ ] 该模块与其余模块**只通过事件/接口通信**,无跨模块 DB 表 join
- [ ] 该模块有自己的**数据所有权**(表归它管)
- [ ] 独立扩容需求(如 `search` 流量大单独拆)
- [ ] 独立发布节奏

**规划中首要拆分:`auth`**(敏感用户域,安全隔离;既定独立服务,详见 §0 / §4 / M3)。
**单体内最可能后续拆:`search` 和 `feed`**(计算重、可独立)。
> 拆分执行前置:先满足上表判据(模块仅经事件/接口通信、数据所有权清晰),再落独立服务,避免边界未清时硬拆。
> 注:现有 `LKM-service` 全部模块均在单体内,拆分是**演进目标**而非现状。

## 九、总体结论

企业级 FastAPI 蓝图 = **以现有 LKM-service(FastAPI 单体 + RabbitMQ 单总线(作为向 Pulsar 迁移的过渡地基)+ APScheduler + GraphQL 只读)为根基**,逐步演进到 **主体模块化单体 + 独立 AUTH 认证微服务 + 事务发件箱驱动的 Pulsar 统一消息总线(`persistent://lkm/biz` 业务域 / `persistent://lkm/auth` 用户域两命名空间单集群多租户)+ 双级缓存(L2 Dragonfly/Redis 兼容 + L1 aiocache)+ RBAC/安全 + OTel→SigNoz 全链路可观察性**;接入层从 nginx 演进到 APISIX,密钥从 .env 演进到 Infisical。用户域以其最敏感的认证数据单独成服务、单独命名空间,在主业务隔离之上再叠一层安全边界。**所有"🔜"演进项以后置增强为原则,不阻塞当前可用系统。**

> **调度最终口径(定案)**:简单 cron/周期触发**统一用 APScheduler + 总线 `cron.*` 触发拓扑**(现状 RabbitMQ cron 拓扑,过渡),**不迁 arq / 不引入 Celery**;**复杂数据管道(ETL/对账/运营日报/回填)演进由 Prefect(或 Dagster)编排,DAG 依赖 + 失败重试 + UI 状态;APScheduler 仅做其简单触发入口**。全文以此为唯一口径。

## 十、实施里程碑与验收标准

> 以现有代码为根基的分步路径,每步有自己的**验收标准**与依赖关系。横向优先级:先打基础、再拆边界、后加容量。

### M0 基础稳定(不动架构)
- **目标**:把当前可运行系统跑在生产级基座上,不引入新总线。
- 动作:生产切 **PostgreSQL(+TimescaleDB 扩展基座,§5.1 hypertable 落地取决于 M1)**,沿用现有 Alembic 迁移;补齐 **Testcontainers(PG + L2 缓存(Dragonfly/Redis 协议兼容镜像)+ Pulsar(官方 `apachepulsar/pulsar` 镜像,测试基建))** 跑真实事务发件箱与 (auth/biz) 事件流;标准化错误码 + 全局 handler(§6.1);配置收口(§6.5.1,敏感项切 Infisical);**确立 APScheduler 生命周期绑定(§5.5):scheduler 随 FastAPI lifespan 起停、`AsyncIOScheduler` 绑事件循环、防多 worker 重复调度(独立 worker-scheduler / 单 owner)、优雅关闭拒新任务**。
- **验收**:PG 上全量迁移可回滚;集成测试绿;`/api` 错误均为统一结构;**app 生命周期测试通过(scheduler 随 lifespan 正确启停、多 worker 无重复调度、shutdown 无悬挂任务)**。

### M0.5 指标前移(监控底座,与 M0/M1 并行或紧随)
- **目标**:提前掌握 QPS/延迟/错误率,不等到 M5 才有指标。
- 动作:接入 `prometheus-fastapi-instrumentator` 自动埋点;**在 `health` 路由同层暴露 `/metrics`**;补业务指标(发帖量、outbox 积压、消息总线(Pulsar;过渡 Rabbit)深度/lag、投递失败计数,见 §6.2);`Grafana` 建基础面板;Sentry 保持错误追踪不变;OTel 埋点先行就绪以对接 **SigNoz(链路+指标一体化,后置启用)**。
- **验收**:`/metrics` 返回指标;Grafana 可查 QPS/P50/P95 延迟/错误率;`/api` 与消息队列有可观测性。
- **依赖**:需 M0 已切 PG 基座;可与 M1 并行(埋点独立于 outbox)。

### M1 一致性补强(事务发件箱)
- **目标**:消除"DB 成功但 MQ 丢事件"缺口。
- 动作:加 `outbox_events` 表(含防锁死字段 `locked_at/locked_by`)+(§5.1 **以 TimescaleDB hypertable 按 `created_at` 时间分区/压缩,relay 只扫最近热 chunk,防积压扫脏**,含清理策略)+ relay 领导者选举(DB 租约 / L2 分布式锁(Dragonfly,TTL 续约)选主,同一时刻仅 leader 扫描投递;leader 内 `FOR UPDATE SKIP LOCKED` 领取 + 陈旧锁清理),业务域写事件走 outbox,relay **投递到 Pulsar `persistent://lkm/biz`**(过渡期仍有 Rabbit 的队列走 Rabbit transport);消费者统一幂等(§5.1 §0)。
- **验收**:模拟 MQ 故障后 replay 补齐事件;重复消费幂等;无丢单;**K8s 多副本下仅一个 leader 在 poll(选举生效,其余副本不轮询)**;**leader 失联后租约超期能被接管、事件无缝续投(failover 自愈)**;leader 崩溃到接管窗口无重复投递(SKIP LOCKED 兜底);stale 锁可回收。

### M2 模块内聚(内容域 / 信息流域)
