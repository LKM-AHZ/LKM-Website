# LKM 实时协议

> 核对日期：2026-11-28。业务推送以 `LKM-service/app/ws/`、各模块 `tasks.py` 为准；
> 桌面接入位于 `LKM-desktop/lib/core/api/lkm_ws.dart`。
> 聊天使用独立的 Tinode 协议，见第 5 节。

## 1. 业务推送的定位

`/api/v1/ws/events` 用于上传登记与站内通知，服务端推送事件，客户端只发送控制帧。
业务写操作走 REST。Redis Pub/Sub 不保存历史，断线期间的事件不会补发；
客户端应在连接或重连后通过 REST 拉取权威状态。

`event_id` 用于去重；`version` 由发布方提供，缺省 0。
服务端不生成全通道递增序列，不保证不同事件间的版本或顺序，不能靠版本号推断消息完整性。

## 2. 连接、鉴权与控制帧

```text
GET /api/v1/ws/events?token=<access_token>&channels=upload,notify
```

| 参数或关闭码 | 语义 |
|---|---|
| `token` | access token；握手复用当前用户鉴权，检查账号状态和会话有效性 |
| `channels` | 逗号分隔的服务端白名单；省略或空值默认 `upload` |
| `upload` | 上传登记事件 |
| `notify` | 通知事件 |
| 4400 | 通道非法 |
| 4401 | token 缺失、无效，或 refresh 尝试更换用户 |

用户 ID 从 token 派生，客户端不能指定他人 ID。Redis 通道格式为 `ws:{user_id}:{channel}`。

服务端在 30 秒未收到客户端文本后发送：

```json
{"type":"ping"}
```

客户端控制帧：

```json
{"type":"pong"}
{"type":"refresh","token":"<new access token>"}
```

`refresh` 重新鉴权，新 token 必须属于当前用户；成功时没有独立确认帧。
其他文本被忽略。当前循环没有独立的 pong 超时关闭，也不会仅因 access token 到期
自动触发断连；客户端需主动刷新 token，并按未授权关闭处理失败。

## 3. 当前事件格式

业务事件以 **`event`** 字段识别，字段直接放在顶层。
`type` 不统一表示事件名：通知中它表示通知业务类型。不存在通用的 `data` 包装。

### 3.1 上传登记：`upload_registered`

文件对象完成登记、事务提交后发送，发布方为 `app/modules/files/tasks.py`：

```json
{
  "event":"upload_registered",
  "event_id":"uuid",
  "version":0,
  "upload_id":"uuid",
  "file":{"id":"uuid","status":"pending"}
}
```

`file` 是登记结果的文件对象，示例仅展示部分字段，防御性分支可为 null。
当前发布方未传固定幂等键和版本，由 broker 为每次发布补 UUID 与 0；
不能假设同一上传的每次广播都共用 event_id。收到后刷新文件状态，不表示审核已通过。

### 3.2 通知：`notification_created`

通知落库提交后发送，发布方为 `app/modules/notification/tasks.py`：

```json
{
  "event":"notification_created",
  "event_id":"notification:<notification_id>",
  "version":0,
  "notification_id":"uuid",
  "type":"<通知业务类型>",
  "payload":{}
}
```

示例的 version 为占位；当前发布方使用通知 UUID 的整数值。
聚合通知的 event_id 会附加聚合次数，不能仅按 notification_id 丢弃后续更新。
客户端收到后拉取通知列表或未读数，以 REST 结果为准。

## 4. 重连、补偿与服务端边界

推荐处理顺序：

1. 用当前 access token 建立连接，订阅所需通道，并暂存收到的业务帧。
2. 通过 REST 拉取文件、通知和未读数等权威状态。
3. 应用暂存和后续事件；按发布方的 event_id/version 语义去重，必要时再次刷新。
4. 异常断线按指数退避重连；token 过期前主动刷新，发送 `refresh`。

| 组件 | 位置 | 约束 |
|---|---|---|
| 握手、心跳、续期 | `app/ws/router.py` | 复用 `core.ports.authz.resolve_current_user` |
| 连接与扇出 | `app/ws/manager.py` | 每进程独立连接表，多进程依赖 Redis 广播 |
| 发布与通道白名单 | `app/ws/broker.py` | 未知通道丢弃；Redis 不可用时不阻塞业务 |
| 在线状态 | `app/ws/manager.py` | Redis 计数及 TTL；不可用时只反映本进程连接 |

payload 不可 JSON 序列化时抛错；Redis 发布失败记录日志并返回。
单次向客户端发送有 5 秒上限，发送失败会摘除连接。
新增事件必须同时明确 REST 补偿入口、发布方幂等键与版本含义，并同步客户端及本文。

## 5. Tinode 聊天接入

聊天不经过 LKM `notify` 通道。Compose/K8s 的 Tinode 服务由网关转发 `/v0/*`；
AUTH 内部账号桥位于 `auth/router_internal_tinode.py`，对公网拦截，并额外校验桥接令牌。

当前桌面实现：

- 连接 `ws(s)://<LKM host>/v0/channels?apikey=<client API key>`；
  API key 与服务端 `LKM_TINODE_API_KEY_SALT` 配对，客户端通过
  `--dart-define=TINODE_API_KEY=...` 注入。生成命令见根 `.env.example`。
- 先发送 `hi`，再以 `scheme=basic`、`secret=base64("lkm:" + access_token)` 登录。
- AUTH 验证 LKM 会话与聊天封禁状态；首次登录由 Tinode 建号，随后 `link` 回调保存
  `tinode_links`。桥原样保存回传 uid，不自行增删 `usr` 前缀。
- 房间 ACL、消息持久化、历史拉取和已读序号由 Tinode 承载；客户端实现和对应测试在
  `LKM-desktop/lib/chat/tinode/`、`test/chat/tinode_client_test.dart`。
- 当前桥在换发身份时检查聊天封禁；已建立的 Tinode 会话存在到期窗口，需要在目标环境验收。

此处只记录 LKM 的接线约定；Tinode 完整帧类型、请求关联和错误处理应与实际服务版本及客户端测试一起维护。
