# LKM 实时协议（WebSocket）

> 日期：2026-11-15
> 范围：LKM-service 的 `/api/v1/ws/events` 客户端协议；聊天由自托管 Tinode 的
> `/v0/*` 协议承载，不在本文范围内（见 `superpowers/specs/2026-11-15-chat-system-design.md`）。
> 代码事实以 `LKM-service/app/ws/` 与 `LKM-service/app/modules/*/tasks.py` 为准。

## 1. 定位

LKM 的 WebSocket 是**单向推送 + 少量控制帧**：服务端推送业务事件，客户端不需要在连接上
发送业务命令（写操作一律走 REST）。设计目标是“实时体验增强”，不是可靠消息通道：

- 推送失败或连接中断不阻塞主流程；客户端通过 REST 补偿。
- 每个事件带 `event_id` 与 `version`，用于去重与丢弃旧帧。
- 断线重连后先拉 REST 状态，再恢复订阅。

## 2. 连接与鉴权

```
GET /api/v1/ws/events?token=<access_token>&channels=upload,notify
```

| 参数 | 说明 |
|---|---|
| `token` | 短期 access token；握手时校验用户存在、锁定、token_version、改密状态 |
| `channels` | 逗号分隔；缺省只用 `upload`；非法通道直接 4400 关闭 |

通道白名单由服务端维护（`app/ws/broker.py` 的 `CHANNELS`）。当前：

| 通道 | 用途 |
|---|---|
| `upload` | 直传对象登记完成（`upload_registered`） |
| `notify` | 站内信/业务通知（`notification.created` 等） |

Redis 通道名为 `ws:{user_id}:{channel}`，`user_id` 由服务端从 token 派生；客户端无法
订阅他人通道。

关闭码：

| code | 含义 |
|---|---|
| 4400 | `channels` 非法 |
| 4401 | token 缺失/无效/续期换身份 |

## 3. 帧格式

### 3.1 服务端 → 客户端（业务事件）

```json
{
  "event_id": "uuid",
  "version": 0,
  "type": "upload_registered",
  "event": "upload_registered",
  "data": {}
}
```

- `event_id`：幂等键；同一次事件重推时逐字段一致，客户端据此去重。
- `version`：调用方单调版本号，缺省 0；客户端可按 `(event_id, version)` 丢弃旧帧。
- `type` / `event`：现有 payload 两处都有，客户端以 `type` 为主、`event` 兼容旧客户端。
  新事件统一使用 `type`，`event` 可保留同值。

### 3.2 服务端 → 客户端（控制帧）

```json
{"type": "ping"}
```

服务端在 30 秒无客户端文本时发送 `ping`；客户端必须尽快回 `pong`。

### 3.3 客户端 → 服务端（控制帧）

```json
{"type": "pong"}
{"type": "refresh", "token": "<new access token>"}
```

- `pong`：刷新活跃窗口。
- `refresh`：连接存活期内续期；新 token 必须与当前连接同一 `user_id`，否则 4401 关闭。
- 其它文本：忽略并保持连接。客户端不要用 WS 发业务消息。

## 4. 已知事件

### 4.1 `upload_registered`（`upload` 通道）

直传对象完成登记后推送。示例：

```json
{
  "type": "upload_registered",
  "event": "upload_registered",
  "event_id": "uuid",
  "version": 0,
  "data": {
    "upload_id": "uuid",
    "file_id": "uuid",
    "status": "pending"
  }
}
```

客户端收到后刷新文件列表或轮询文件详情；不要假设文件已审核通过。

### 4.2 `notification.created`（`notify` 通道）

站内信/业务通知落库后推送，`data` 至少包含通知 id、类型与跳转载荷。客户端收到后
增加未读计数并拉取通知列表；未读真值以 REST 为准。

### 4.3 聊天

聊天不经过 LKM WS。客户端按 Tinode `/v0/channels` 协议连接；LKM 只负责账号桥
（`/api/v1/auth/internal/tinode/*`）与网关 `/v0/*` 路由。不要把 Tinode 消息混入
`notify` 通道。

## 5. 客户端重连与补偿

推荐顺序：

1. 用当前 access token 建立 WS，订阅所需通道。
2. 连接成功或重连成功后，先调用相关 REST 列表/详情接口拉一次权威状态
   （文件列表、通知列表或未读数）。
3. 再应用 WS 推送；对 `(event_id, version)` 去重。
4. 连接异常按指数退避重连（桌面端现有实现：`LKM-desktop/lib/core/api/lkm_ws.dart`）。
5. access token 过期前用 `refresh` 续期；`refresh` 被拒即按未授权处理，重新登录。

服务端不保证事件顺序跨通道；同通道内 `version` 单调，但客户端仍应以 REST 状态为准。

## 6. 服务端实现与约束

| 组件 | 位置 | 约束 |
|---|---|---|
| 握手/心跳/续期 | `app/ws/router.py` | 鉴权复用 `core.ports.authz.resolve_current_user` |
| 连接表/扇出 | `app/ws/manager.py` | 每进程独立；多副本依赖 Redis 广播 |
| 通道白名单/发布 | `app/ws/broker.py` | 发布 fail-open；未知通道静默丢弃 |
| 事件产生 | 各模块 `tasks.py` | 优先在事务提交后发布；不要阻塞主写路径 |

发布约束：

- payload 必须可 JSON 序列化；不可序列化直接抛错（调用方 bug）。
- Redis 未配置/不可用时静默 no-op，不阻塞业务。
- 发送慢客户端有 5 秒上限，超时摘除连接，避免拖住同进程其他用户。

## 7. 新增通道/事件的检查清单

1. `app/ws/broker.py` 的 `CHANNELS` 加通道名。
2. 发布方用 `publish(user_id, channel, payload)`；跨进程 worker 里发布。
3. 客户端 `channels` 参数同步；旧客户端不订阅新通道时不收，不影响主流程。
4. 若事件需要可靠补偿，必须同时提供 REST 查询入口；WS 不是可靠通道。
5. 更新本文与 `docs/后端架构与现状.md` 的可观测性/实时章节。
