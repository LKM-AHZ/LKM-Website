# 后端消息总线与插件化重构方案

> 状态：步骤 1–9 全部完成（跨模块白名单 43 → **0**，间接依赖亦纳入约束；`content` 已按域
> 拆成 `qa`/`comment`/`blog`/`columns` 四个独立模块，自身只剩 5.3k 行；L2 跨域协作统一走
> `core/ports` 端口契约，早期命令总线骨架已删除，见 ADR-007）
> 范围：`LKM-service`（`core/`、`app/`、`boot/`、`auth/`）
> 原则：先结构、后插件；每个提交可独立回滚且行为不变

---

## 0. 一句话结论

这个后端已经是「模块化 + 事件总线」的半成品。真正的缺口不在「有没有总线」，而在
**总线只覆盖了异步路径，请求路径上的跨域耦合仍是直接 import**。因此本轮重构的目标不是
「造一条新总线」，而是把已有的三套机制（事件总线、端口注册表、路由/任务注册表）收敛成
一套可校验的模块契约，并让模块发现从「手写元组」变成「清单扫描」。

步骤 1–5 是这一层的**结构准备**（零行为变化），步骤 6–9 才改变调用拓扑。

## 1. 现状诊断

### 1.1 职责

| 症状 | 证据 |
|---|---|
| 一个文件六种职责 | `core/messaging.py` 760 行同时承担：routing_key→topic 映射、命名空间隔离校验、envelope JSON Schema 构造、Pulsar/RabbitMQ 传输选择、消费线程生命周期与 ack/nack、契约校验与失败指标。 |
| 模块粒度失真 | `app/modules/content` 9693 行；`app/modules/admin` 3820 行。两者都远超一个业务域。 |
| 伪模块 | `admin.review_service` 直接读 `content.models` / `files.models` / `projects.models` 三张表——它是跨域读模型，不是一个业务域。 |
| 注册信息三处重复、形状各异 | `app/modules/registry.py` 的 `MODULES`、`_ERROR_MODULES`，与 `app/bootstrap.py` 的 `APP_MODEL_MODULES` / `APP_TASK_MODULES`。`registry.py` 的 docstring 直接写着「模型与任务须另在 `app.bootstrap` 登记，不能只修改本表」——把已知缺陷写成了规范。 |

### 1.2 耦合（量化）

`messaging.publish` 的调用点只有 `outbox_relay`、`scheduler`、`jobs`、`metrics_relay`，
即**总线只服务异步事件**。而模块之间在事务内的调用全是直接 import：

- `content.service` → `from app.modules.points.service import reward, spend`，并直接调
  `enqueue_points_event` **在 points 的 outbox 里写事件**（跨域写方向耦合）；
- `files.service` → `projects.models` 校验项目归属；
- `content.repository` → `exam.models` 读考试证书判定发帖资格。

这些恰好都发生在同一事务内，是边界最需要约束的地方，却完全没有边界。

import-linter 的「业务模块间不任意依赖」合同挂了 **43 条 `ignore_imports`**：

- content 作为源 10 条、作为目标 14 条——事实上的中心节点；
- 合同还设了 `allow_indirect_imports = "true"`，间接依赖不计入，**实际耦合比 43 更宽**；
- 合同只校验 import 形态，不校验语义。

新增一个业务域要改 4 处、跨 2 个包；漏改的表现是运行时 404 或缺错误码，而不是启动失败。

### 1.3 可测试性

- 模块间是 import 级耦合，测一个域必须拉起整张 import 图。重构前只有两个缝合点：
  `core.messaging.set_transport()` 与 `core.ports.registry`（7 个端口、`PortNotBound` fail-fast）。
- 端口只在 **app↔auth** 之间建立，**模块↔模块没有等价物**，因此「换实现/注入假实现」
  对业务域不可用。
- 5 个全局可变注册表（`_impls` / `_extra_routers` / `_TASK_HANDLERS` / `_CRON_JOBS` / `_assembled`）
  靠 `reset()` 兜底，测试顺序敏感。

## 2. 目标结构

### 2.1 边界哲学：不要把所有调用都搬上总线

按一致性需求分三层，这是整个方案的前置决策：

| 层 | 场景 | 机制 | 事务语义 |
|---|---|---|---|
| **L1** | 域内调用 | 自由调用 | 同事务 |
| **L2** | 跨域同步、必须强一致 | **进程内端口契约**（`core/ports/<domain>.py`，显式签名 + 强制传入调用方 `db`） | 同事务 |
| **L3** | 跨域异步、可最终一致、跨进程 | Pulsar/RabbitMQ + outbox | 最终一致 |

把 L2 的调用直接改走 L3 是**行为改变**（强一致 → 最终一致），必须单独评审，
不能混进「行为不变」的重构。

### 2.2 目标包结构

```
core/bus/
  __init__.py        # 对外入口
  topics.py          # routing_key / topic / 订阅清单 / 命名空间隔离校验
  schema.py          # envelope JSON Schema 与编码
  contracts.py       # 契约校验、永久失败判定
  runtime.py         # 发布路径：编码 → 契约 → props → 选 transport → 投递（内含 Pulsar 默认实现）
  consumer.py        # 消费路径：订阅线程、ack/nack、超时
  transports/
    base.py          # Transport 协议
    rabbitmq.py      # 备选实现
    inmemory.py      # 测试/离线替身
core/ports/
  registry.py        # 端口注册表、REQUIRED_PORTS、装配期 validate_all() fail-fast
  <domain>.py        # L2 契约：每个域一组函数签名 + 语义说明，实现由 bootstrap 绑定
core/plugins/
  manifest.py        # manifest.toml 的通用加载与形状校验
  host.py            # 插件宿主：发现 → 校验 → 定序安装（步骤 8）
app/modules/<domain>/manifest.toml   # 插件清单
core/messaging.py    # 兼容垫片（只 re-export，无实现）
```

依赖方向（由 import-linter 强制）：

```
boot ──→ app ──→ core          boot ──→ auth ──→ core
app.modules.X ──→ core.ports.<domain>      （L2，同事务）
app.modules.X ──→ core.bus                 （L3，异步事件）
app.modules.X ──→ app.contracts            （跨域 DTO）
app.modules.X ──→ app.modules.Y:__init__   （仅公共 API，白名单已清零）
```

### 2.3 示例一：插件清单（已落地）

替代散落在两个包里的四个手写元组。

```toml
# app/modules/points/manifest.toml
name     = "points"
errors   = ["app.modules.points.errors"]
models   = ["app.modules.points.models"]
tasks    = ["app.modules.points.tasks"]
# provides / requires 供步骤 8 的依赖校验使用，当前留空
```

派生规则见 `app/modules/spec.py`：`MODULES` / `ERROR_MODULES` /
`APP_MODEL_MODULES` / `APP_TASK_MODULES` 全部由清单生成，顺序与拆分前逐项一致。

### 2.4 示例二：L2 端口契约（已落地）

```python
# core/ports/points.py —— 契约：只有函数签名与语义，没有任何实现
async def reward(
    db: AsyncSession, user_id: uuid.UUID, delta: int, reason: str,
    ref_type: str, ref_id: str, *, allow_negative: bool = False,
) -> Any:
    return await get("points_writer").reward(...)
```

```python
# app/bootstrap.py —— 实现类：装配期绑定，只有它内部才 import points
class _PointsWriterImpl:
    async def reward(self, db, user_id, delta, reason, ref_type, ref_id, *, allow_negative=False):
        from app.modules.points.service import reward
        return await reward(db, user_id, delta, reason, ref_type, ref_id,
                            allow_negative=allow_negative)
```

```python
# app/modules/content/service.py —— 消费方：只依赖 core.ports.points
# 之前：from app.modules.points.service import reward, spend
await points_port.enqueue_event(db, author_id, "post", f"item:{item.id}")
```

`db` 由调用方传入、与被调方共用同一 session（端口签名里就是第一个参数）。这是「行为不变」
的技术前提（见 §4 风险 1）。

**为什么最终不是「按名字分发的命令总线」**：步骤 5 先落了 `core/bus/dispatcher.py` 骨架，但
步骤 6 迁移 43 条白名单时，端口契约同时在静态签名、`db` 必填、装配期 fail-fast 三点上都更强，
dispatcher 全程零调用方，最终在收尾时删除（ADR-007）。

### 2.5 示例三：插件宿主（步骤 8，已落地）

最终形态是「清单在 `core.plugins` 校验定序，`app.modules.spec` 在导入期派生四张表」：

```python
# core/plugins/host.py —— 已落地
class PluginSet:
    def validate(self) -> tuple[Manifest, ...]:
        """重名 / 能力重复提供 / requires 闭包 / 无环 —— 缺一即启动失败；返回安装顺序"""

    def install_order(self) -> tuple[Manifest, ...]:
        """稳定 Kahn 定序；顺序即路由注册顺序；成环抛错而不是返回半截列表"""

def discover_entry_points() -> tuple[Manifest, ...]:
    """读第三方发行版的 entry_points(group="lkm.plugins")，按入口点名排序"""
```

`validate` 直接返回定序，是因为调用方几乎总要紧接着取顺序：分两次算拓扑排序没有收益，
而漏调第二次会让「校验通过但不按依赖装」这类错误无声发生。`install_order` 单独被调用时
成环即抛 `PluginError`——早期实现会 `break` 并返回短列表，后果是部分模块静默消失
（路由/模型/错误码全丢）而进程照常启动。

```python
# app/modules/spec.py —— 清单 → 四张注册表（模块导入期完成）
ordered = PluginSet((*load_manifests(_MODULES_DIR), *discover_entry_points())).validate()
SPECS = tuple(_to_spec(m, builtin=m.name in builtin_names) for m in ordered)
# MODULES / ERROR_MODULES / APP_MODEL_MODULES / APP_TASK_MODULES 均由 SPECS 展平
```

外部插件（`builtin=False`）另有两条装配期约束，都指向「不报错、运行时才发作」的故障：

- `module` 必须声明（没有 `app.modules.<name>` 可回退），且 `find_spec` 能解析——写错路径
  会在发现期报出插件名，而不是装配期抛裸 `ModuleNotFoundError`；
- `module` 不得落在 `app` / `auth` / `boot` / `core` 内：指向宿主包会让同一模块被二次装载
  （`ROUTERS` 挂两次、错误码重复注册），而 import-linter 合同看不到外部发行版，等于绕过
  全部边界校验。

清单里的 `routers` / `graphql` 两个字段**已删除**：它们只被解析、没有任何读取方（出口实际
由模块 `__init__.py` 的 `ROUTERS` / `GRAPHQL` 约定提供），第三方插件照着写只会拿到 0 条
路由与一串 404。删掉后写它即命中「未知字段」拒收。

`boot.assemble()` 因此**不再负责发现插件**，只做两侧注册汇总与端口校验：

```python
app.bootstrap.register(); auth.bootstrap.register()
ensure_all_models(); import_task_modules(); ports.validate_all()
```

「装配漏模块」于是在 `import app.modules.spec` 时就暴露（清单缺失/重名/成环），而不是等到
访问路由时 404。

## 4. 风险与测试保护

### 4.1 高危（语义可能真的变了）

| 风险 | 触发步骤 | 具体失效 | 保护 |
|---|---|---|---|
| **事务边界** | 6 | 被调方自开会话 → 跨域写不再原子：内容发布失败而积分已入账 | 端口函数第一条参数就是 `db`（`core/ports/points.py` 每条都收）；断言「回滚后 points ledger 无残留」 |
| **一致性口径** | 6 | 强一致退化为最终一致 | `item:{id}` ledger ref 幂等、`content.counters` 对账、`app/flows` 作回归 |
| **`allow_indirect_imports` 改 false** | 7 | 一次性暴露隐蔽间接依赖 | 先跑「仅报告不阻断」扫描，把新暴露项补进清单再逐条清 |

### 4.2 中危（行为应不变，但极易改坏）

| 风险 | 触发步骤 | 保护 |
|---|---|---|
| 消费线程 ↔ asyncio 桥接（`run_coroutine_threadsafe` + ack/nack） | 1、2 | `tests/test_messaging.py` 断言全绿 |
| **拆分后 monkeypatch 目标失效** | 1、2 | 见 §4.3 |
| 注册表搬移导致模块**静默丢失**（只表现为 404/缺错误码） | 3、4 | 启动断言 + `tests/test_module_spec.py` 等价性 |
| `_assembled` / `_registered` 幂等标志 + `reset()` 泄漏 | 3、4 | 会话级 fixture；「双次 assemble 为 no-op」测试 |
| fail-fast 端口语义被放宽 | 8 | 保留 `PortNotBound`；插件加载失败必须让 boot **失败** |

### 4.3 专条：拆分模块会打断 monkeypatch（本次实测踩到）

`tests/test_messaging.py` 通过 `monkeypatch.setattr(messaging, "_CONSUMER_RETRY_S", ...)`
之类的方式改写模块级全局。实现搬到 `core.bus.consumer` 后，对**垫片**属性的改写不再影响
真实实现（模块级常量在导入时已绑定）。

已落地的处理方式：

1. 垫片只保留 re-export，**不承载任何实现**，也**不再导出**可变状态（`_client` /
   `_producers` / `_closed` / `_CONSUMER_RETRY_S`）；
2. 测试的 patch 目标改为**新模块**（`core.bus.consumer` / `core.bus.runtime` /
   `core.bus.transports.rabbitmq`），断言内容一字不改；
3. 局部变量名与模块名的冲突（测试里的 `consumer = Mock()`）用带前缀的别名隔离
   （`bus_consumer` / `bus_runtime` / `bus_schema` / `bus_topics`）。

这与「配置服务拆分导致测试 monkeypatch 失效」是同一类陷阱，属已知坑。

**同一类坑在步骤 6 又出现一次**：`content/service.py` 的 `enqueue_points_event` 改成
`points_port.enqueue_event` 后，`tests/test_content_interactions.py` 里
`monkeypatch.setattr(content_service, "enqueue_points_event", spy)` 立刻失效（属性已不存在）。
处理方式同上：把桩改挂在**新的调用点**（`core.ports.points.enqueue_event`），断言不变。
规律是：**凡是把「模块级名字」换掉的重构，都要同步检查测试的 patch 目标**。

### 4.4 安全（纯机械）

步骤 1、2 属纯搬移，`pytest && lint-imports` 通过即可回滚。步骤 5 的命令总线骨架最终未被
采用，已在收尾提交里删除（ADR-007）。

## 5. 决策记录（ADR）

### ADR-001：总线分三层，不把同步调用一律改成事件

- **背景**：需求是「用通用消息总线沟通的模块化后端」。
- **选项**：A. 所有跨模块调用走消息总线；B. 按一致性分三层。
- **决定**：B。L2 用**进程内端口契约**（同事务，`db` 由调用方传入），L3 用 broker
  （最终一致）。
- **理由**：A 会把 `content → points` 记账这类同事务强一致操作降级为最终一致，属于
  行为改变，违反「重构不改行为」；且会引入一个无法回滚的一致性窗口。
- **代价**：两套机制的状态不同——L2 靠 `ports.validate_all()` 在**装配期** fail-fast，
  L3 靠 `core/bus/contracts.py` 在**发布/消费期**校验；端口调用本身不经过总线契约，
  它的正确性靠类型系统 + 各域等价性测试。早期按字符串分发的命令总线形态已被证伪并删除，
  见 ADR-007。

### ADR-002：模块发现用清单文件，而不是 Python 常量

- **决定**：`app/modules/<name>/manifest.toml`，由 `core/plugins/manifest.py` 扫描。
- **理由**：当前新增模块要改 4 处；清单让「注册」成为模块自己的事，且可被工具校验。
- **代价**：清单与代码可能不一致 → 用启动期断言 + 等价性测试 + 「每个包必须有清单」测试兜底。

### ADR-003：先结构后插件

- **决定**：步骤 1–5 全部零行为变化，再迁移白名单（6–7），最后才做插件加载（8）。
- **理由**：在 43 条耦合尚未建模时先做插件化，会把不确定性放大。

### ADR-004：Pulsar 不搬进 `transports/`

- **背景**：步骤 2 原计划把 pulsar/rabbitmq/inmemory 三者都抽到 `core/bus/transports/`。
- **决定**：只抽 rabbitmq 与 inmemory；Pulsar 作为**内置默认实现**留在 `core/bus/runtime.py`。
- **理由**：Pulsar 的 `_client` / `_producers` / `_closed` 是 **bus 级生命周期**，与
  `runtime.publish` / `shutdown` 同寿；消费线程（`consumer.py`）也要复用同一 client 与
  同一把锁。把它搬进 transports 会把一个生命周期撕成两半，并迫使 closed 状态在两处各存
  一份——两份状态必然漂移，而 `shutdown` 与「in-flight 建 producer/consumer」的竞态正是
  现有测试（`test_shutdown_discards_*_created_in_flight`）重点守护的地方。
- **代价**：`transports/` 目前只覆盖两个可替换实现；将来若真的需要多 broker 并行，
  应先定义「含消费侧」的完整 Transport 接口，再整体搬迁，而不是只搬发布侧。

### ADR-006：端口访问器默认惰性，导入期取值必须留占位

- **背景**：`admin_guard` 端口要在**路由模块导入期**返回 FastAPI 的 `Depends` 对象，
  因为 `Annotated[CurrentUser, Depends(...)]` 在模块级求值。
- **踩到的坑**：直接 `get("admin_guard")` 让 `import app.main` 在未装配时抛 `PortNotBound`，
  破坏了既有的「装配时序」不变量——`tests/test_boot_assembly_order.py` 用一个刻意反序的
  子进程证明：反序时应用**仍能构建**，只是静默丢 auth 路由。
- **决定**：端口未绑定时返回一个**请求期才失败**的占位依赖（fail-closed，不会匿名放行），
  从而不改变 import 期契约。
- **通则**：端口访问器默认惰性（请求期解析）；只有被框架要求在导入期取值时，才允许提前
  解析，且必须提供一个「未装配时安全失败」的占位实现。

### ADR-005：清单按目录名排序

- **决定**：`load_manifests` 按目录名排序返回，不引入 `order` 字段。
- **理由**：目录扫描顺序在各文件系统上不保证一致，而模块顺序决定路由注册顺序。
  排序让结果确定；顺序本身的语义由 `tests/test_module_spec.py` 的等价性测试钉住——
  新增模块若改变了顺序，测试会立刻失败并要求人工确认。
- **代价**：`MODULES` 的顺序被隐式绑定到字母序（当前恰好与旧顺序一致）。

### ADR-007：L2 的最终形态是端口契约，不是命令总线

- **背景**：步骤 5 落了 `core/bus/dispatcher.py`——按字符串注册/分发、handler 约定必填
  `db` 的进程内命令骨架。步骤 6 迁移 43 条白名单时，实际采用 `core/ports/<domain>.py`：
  每个域一份显式函数签名，实现由 `app.bootstrap` 装配期绑定，`validate_all()` 缺一即启动
  失败。到步骤 9 结束，dispatcher 仍**零生产调用方**，只剩 8 项单测维持存在感。
- **选项**：A. 把已迁完的调用改回 dispatcher；B. 两套并存；C. 删除 dispatcher，L2 只留端口。
- **决定**：C（收尾提交）。
- **理由**：
  1. 端口有**静态签名**：调用方拿到具体函数，`ruff`/`ty`/IDE 都能查；dispatcher 按字符串
     分发，命令名拼错要到运行期才炸。
  2. 端口的 `db` 是**签名的一部分**，比「handler 侧约定必填」更难写错。
  3. 两套机制并存会让「跨域协作该走哪个」变成每次都要解释的问题；而 dispatcher 在 6–9
     全程无调用方，保留它等于给后来者留一个错误示范。
  4. 「用总线沟通」这个需求由 L3（Pulsar + outbox）与 L2（端口契约）共同满足，不缺
     dispatcher。
- **代价**：新增一条跨域能力要改三处（`core/ports/<domain>.py`、`app/bootstrap.py` 的实现类、
  `REQUIRED_PORTS`）——这是「显式登记」的代价，但漏改会在**装配期** fail-fast，而不是运行时
  404。这套登记的一致性由 `core/ports/registry.py` + `boot/assemble.py` 的 `validate_all()`
  保证。
- **可回滚**：骨架与 8 项测试在 `3d9375e` 可完整取回。
