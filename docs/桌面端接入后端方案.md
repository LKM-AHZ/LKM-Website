# 桌面端（Phientist / 理科迷）接入 LKM-service 方案与逐项审核

> 范围：把 `LKM-desktop` 从 Solian 后端（`https://api.solian.app` + `solar_network_sdk`）迁到本仓库的
> `LKM-service`（`/api/v1`）。目标是让桌面端最终替代 `LKM-official-website` 的功能面。
>
> 核对日期：2026-11-08（依据 `LKM-service/tests/contracts/openapi.json` 与 `LKM-desktop` 当前工作树）
>
> 结论先行：**这不是"改 baseUrl"的迁移，而是换域模型的数据层重建**。可迁移的对位只有
> 认证/账号、通知、文件、积分、互动这五块；帖子（sphere）、领域（realms）、私聊（chat）、
> 多币种钱包（wallet）、贴纸、工单、问卷、动态（thoughts）在 LKM-service 没有对应物，
> 应当删除而不是移植。

## 2. 架构决定

**D1（核心）** 新建 `lib/core/api/`，包含：

- `api_client.dart`：dio 封装，负责 baseUrl（`$server/api/v1`）、Bearer 注入、`ApiResp` 解包、`code != 0` 抛 `ApiException(code, message, requestId)`、401/`AuthErr.TOKEN_*` 触发刷新重放。
- `api_session.dart`：令牌唯一持有者（内存单例 + prefs 持久化），轮换写回，并发刷新合并。
- 域 Repo：`auth_api.dart` `users_api.dart` `notification_api.dart` `files_api.dart` `content_api.dart` `interaction_api.dart` `points_api.dart` `treehole_api.dart` `search_api.dart` `timeline_api.dart` `admin_api.dart`。

**D2** 不改造 `solar_network_sdk` 内部，也不做 Solian→LKM 的服务端兼容网关。桌面端直接换实现，Solian 专属域连 UI 一起删。

**D3** 信封与错误码只在 `ApiClient` 一层处理；上层 Repo 只抛领域异常。

**D4** 能力/版本探测改为 `/api/v1/health`（静态）+ `/api/v1/readiness`（依赖就绪），`server_compatibility.dart` 的 `kRequiredServerCapabilities` 重新定义。

**D5** WebSocket 独立重写（`lib/core/api/ws.dart`），不继承 `SolarWebSocketService`；只承载 upload 事件与通知，不承载私聊。

**D6** 不保留双后端共存。一个版本只认一套后端；共存会让 199 个调用点全部长出分支。**（决策 1 已确认）**

## 4. 逐项审核

判定口径：**通过** = 依据成立、可直接做；**调整** = 方向对但有条目缺陷，按下述修正后做；
**需决策** = 涉及产品或范围取舍，需拍板；**否决/暂缓** = 不做。

| 编号 | 结论 | 审核意见 |
| --- | --- | --- |
| P0-1 | 通过 | 关键点是"业务错误走 200"，`ApiClient` 必须按 `code` 判定，不能依赖 dio 抛错。补充：`X-Total` 头承载分页总数（`core/err.py:_wrap_result`），分页 Repo 要读它 |
| P0-2 | **调整** | 现有一套刷新逻辑分散在 `main.dart`、`account_pod.dart`、`network.dart`、`websocket.dart` 四处读 prefs；而 LKM 刷新是**单次有效轮换**，任何一次并发读旧 refresh token 都会触发 `TOKEN_INVALID` 直接掉登录。必须先把令牌收敛成唯一持有者（P0-2 前置到 P0-3 之前），并显式处理"轮换在途失败→重新登录"路径 |
| P0-3 | **调整（工作量上调）** | 现有登录 UI 是围绕 stargate 的"挑战-因子轮转"写的，LKM 是"选方式-拿令牌"，交互模型不同，1464 行基本重写而非改接口。另外 passkey 两端都支持但对齐成本高，P0 只做密码 + 邮箱码，passkey/2FA/GitHub OAuth 与找回密码后置（决策 6 已锁定） |
| P0-4 | 通过 | 桌面端已有服务器地址设置项，只需换默认值与探测端点。注意 `/meta` 不存在，`server_compatibility.dart` 的 `/meta capabilities` 与必需集 `{auth,accounts,chat,posts}` 整体失效，须重写而不是改常量。决策 5 已定：设置页只填域名，路径前缀由 `ApiClient` 拼 |
| P0-5 | 通过 | 收尾动作，风险低；`route.gr.dart` 等生成物要走 `build_runner` 重生成 |
| P1-1 | **需决策** | `/timeline` 是什么内容流需与后端确认语义（`GET /api/v1/timeline` 只有 1 条路径、无分页参数文档）。另外 Solian post 没有"板块/专栏"概念，`ContentCard` 不能复用 `posts/widgets` 组件，需要新组件；不要指望"组件零改动" |
| P1-2 | 通过 | 评论是两级扁平结构，与 Solian 的嵌套 replies/post chain 不同，UI 需去掉"链式回复"层 |
| P1-3 | 通过 | 端点齐（me / unread-count / read / preferences / tokens）。依赖项：FCM/APNs 项目未建（桌面端 `google-services.json` 仍指向 `dev.solsynth.solian`），推送注册在 P1 只能算半通 |
| P1-4 | **调整** | LKM 用户域极薄：46 个 accounts 方法里的徽章、社交分、日历、隶属、改名卡全部无对位。P1-4 只做"资料 + 关注"，其余用户中心内容同步从 UI 删除，否则会做出大片空壳页 |
| P1-5 | 通过 | `/search`（meilisearch）+ `/search/status`，语义清晰 |
| P2-1 | **调整** | 发内容涉及板块/专栏的准入（`boards/applications`、`columns/plan` 有配额与审核）。首个版本应只允许发到已加入的板块/默认时间线，把"申请开板"留给 P3 |
| P2-2 | 通过 | `interaction`（点赞/收藏/历史/浏览）+ `items/{id}/forward` 覆盖；注意点赞与收藏是两个独立端点，不能合成一个"reaction" |
| P2-3 | **通过（已决策）** | LKM 上传产物默认 `PENDING` 待审核，用户传完立刻看不到自己的图。已拍板：显示「审核中」占位，审核通过后替换为实图、驳回则移除并提示（决策 3）。另外 S3 presigned 直传需要桌面端能自带 `Content-Length`/`Content-Type`，现有上传器要重写而非改参数 |
| P2-4 | **调整** | LKM WS 只做"通知上传事件 + 推送通道"，没有 Solian 的 ack/断线续传，也没有私聊。P2-4 只能替代进度与通知推送，不能替代 chat；不要让 WS 层承诺"消息不丢" |
| P3-1 | 通过 | 树洞 17 条路径完整，且有会话/撤回/举报 |
| P3-2 | **调整** | `/points` 是单一积分账户，不是 19 个 wallet 方法覆盖的多币种钱包/订单/兑换单。P3-2 只能做"积分+签到+台账+排行"，钱包 UI 属 P4-1 删除范围，别混进来 |
| P3-3 | 通过（工作量大） | 网站已有 forum/qa/projects 页面可参照，但要新写 4 套列表+详情+编辑，是本计划最大的一块 UI 工作量 |
| P3-4 | 通过 | `/exam/*`、`/starhope/*` 在位 |
| P3-5 | **通过（已决策：做）** | 原「暂缓」意见作废（决策 4）。LKM 的 39 条 admin 路径对应网站 admin 六块页面，桌面端要覆盖这些页面而不是 stargate 的 9 个「惩罚/安全偏好」方法。开工前必须先落管理员角色门（`/auth/me` 的角色位）与审核队列视图，否则入口会裸露；工作量与 P3-3 同级 |
| P4-1 | **调整（顺序）** | 不能一次性删。删域必须"该域新实现上线后逐域摘除"，否则中间态无法回归。另外 `lib/thoughts/` 下有两样东西：Solian 动态流（删）与本地仪表盘组件（保留），要拆开处理 |
| P4-2 | **调整** | `solar_network_foundation` 不只是 SDK 依赖，`lib/core/auth_wiring.dart` 用它做提权流程；删 SDK 后这股线要么重写要么保留该包。裁剪边界按"引用为零"逐个删，不按包名一刀切 |
| P4-3 | 通过 | 但 Linux 打包当前 `libsecret-1-dev` 缺失，属于环境前置，不在本计划范围 |

### 4.1 跨条目风险（审核后新增）

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| R1 双后端期不可维护 | 199 个调用点若都要"看服务器走哪套"，代码会长满分支 | 采纳 D6：不共存，单版本切换 |
| R2 账号无法迁移 | Solian 与 LKM 是两套用户库（密码哈希、refresh 表都独立），老用户不能平滑登入 | 已决策不做迁移（决策 2）：新版本=重新注册，不做重置引导；风险已接受，发布说明注明 |
| R3 缺验收环境 | 本地 `127.0.0.1:8000` 当前未运行，契约测试无活后端，所有验收都会退化成"编译通过" | 每期开工前 `docker compose up` 起全栈，或对 `tests/contracts/openapi.json` 起 mock |
| R4 契约漂移 | `openapi.json` 是测试产物，若后端改动未同步，客户端按它写会错 | 把"`openapi.json` 与实现一致"纳入后端 CI（已有基础），客户端只认该文件 |
| R5 未用代码生成 | 246 条路径手写 Repo 有遗漏风险 | 暂不引入 openapi codegen（`ApiResp` 信封需二次处理、领域模型仍需手写）；用契约测试补：每个 Repo 方法一条对着 openapi.json 的断言 |
| R6 图标/启动图工具链 | `flutter_launcher_icons`/`flutter_native_splash` 硬编码 `ios/Runner`、`macos/Runner`，而本项目是 `ios/Solian`、`macos/Solian` | 与本计划无关但会被打包步骤踩到；P4-3 时手工放置 |

## 5. 决策结果（2026-11-08 已拍板）

| # | 决策 | 结论 | 对计划的影响 |
| --- | --- | --- | --- |
| 1 | 是否接受双后端共存 | **不共存**：一个版本直接切到 LKM-service，回退靠发版 | 确认 D6；199 个调用点不长分支。旧版客户端仍连 Solian 不受影响 |
| 2 | 老 Solian 账号迁移 | **不做** | 无迁移代码、无重置引导；R2 降级为「已知损失，接受」。发布说明里一句话交代即可 |

## 8. 决策 7：AUTH 改为挑战-因子轮转

2026-11-08 追加。三个候选（A 只补 2FA 登录 / B 收敛版 pending_auth / C 完整轮转）中选择 **C**，
后端已落地 `/auth/challenge`（`LKM-service@e3692b6`）。

### 8.1 落地形态

| 步骤 | 端点 | 返回 |
| --- | --- | --- |
| 建挑战 | `POST /auth/challenge` `{account, primary_factor}` | `{id, status, factors:[{kind}], expires_at}` |
| 读状态 | `GET /auth/challenge/{id}` | 同上（重连恢复进度） |
| 提交因子 | `POST /auth/challenge/{id}/factor` `{kind, password?/code?/recovery_code?}` | `pending`（下一批因子）或 `complete`（含令牌） |
| 发验证码 | `POST /auth/challenge/{id}/request` | 统一文案，不泄露账号存在性 |
| 作废 | `POST /auth/challenge/{id}/cancel` | — |
| passkey 选项 | `POST /auth/challenge/{id}/passkey/start` | `PublicKeyCredentialRequestOptions` |
| passkey 断言 | `POST /auth/challenge/{id}/passkey/complete` | `complete`（含令牌）或下一因子 |

**设备标识统一在 `X-Device-Id` 请求头**（`LKM-service@091630f`、`LKM-desktop@c6544933`）。
先前 body 与 query 混用，客户端每加一个端点都得赌一次绑定位置，写错只会得到「挑战不存在」。

密码登录 = 2 RTT（建挑战 + 提交因子）；验证码登录多一次发码。旧 `/auth/login/*` 全部保留。

### 8.2 与 stargate 的差异（刻意不做的事）

1. **不绑 IP**：桌面端 Wi-Fi→热点会让绑 IP 的挑战变成 404。改绑 `device_id` 的 SHA-256。
2. **因子渐进披露**：建挑战只返回第一因子，密码通过后才给后续因子——一次性列全部因子
   等于给攻击者一个「这个账号有没有 passkey」的预言机。
3. **不把 temp_token 落库**：管理员首次强制设置 TOTP 那条路径在挑战内显式拒绝
   `CHALLENGE_UNSUPPORTED_STEP`，继续走 `/auth/2fa/setup/complete/temp`。

### 8.3 尚未接入的因子

`totp`（挑战模型已能接，但当前登录路径 `finalize_auth_response` 恒为 `requires_2fa=False`，
TOTP 只在 step-up 与管理员强制设置里出现）、`passkey`（服务端已有 begin/complete，适配器待写）。
两者都在 `auth.challenge` 的因子位置留好，客户端届时只多渲染一个输入框。

  （`LKM-service@3d2d946`）。旧 `/auth/login/*` 保留，网站与 bot 不受影响。
- 桌面端：按挑战模型重写完成（`LKM-desktop@7640fe77`）。首版按凭据分端点的实现（`824156e8`）
