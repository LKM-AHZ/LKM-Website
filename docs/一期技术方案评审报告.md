## 1. 结论

**按当前落地的技术方案，一期不可交付。** 问题不在「功能没写完」——功能面的自我评级是诚实的；
问题在三条**装配线**：能不能启动、认证边界是否可靠、有没有人证明它能跑通。

| # | 阻断项 | 一句话 | 置信度 |
| --- | --- | --- | --- |
| R1 | ClamAV 缺 healthcheck 却被 `service_healthy` 依赖 | `docker compose up` 在装配期直接失败，报错与业务症状毫无关联 | **高**（已最小复现） |
| R2 | 内部 seam 对公网可路由 + 默认令牌是 `change-me` | `/api/v1/auth/internal/*` 暴露为公网 API，只剩占位符口令保护 | 高（已核验配置） |
| R3 | 社区 admin 可铸 Bot 面板全权票据 | 后台管理员会话被盗 = Bot 控制面失守 | 高（已核验代码） |
| R4 | 没有一条经网关的端到端验收证据 | 唯一金路径脚本直连 `127.0.0.1:8000`，网关层从未被验证 | 高（已核验） |
| R5 | 站点身份配置硬编码（compose 路径） | 按文档换域名后 OAuth/Passkey/回跳/预签名**静默全失效** | 高（条件：域名交付） |

## 2. 阻断项风险登记表

每条统一给定位、触发条件、影响、最小修复、验证方式、推翻条件。

### R1 [blocker] ClamAV 启动前提不成立

- **位置**：[docker-compose.yml](../docker-compose.yml) 第 626–637 行（clamav 服务块，**无 `healthcheck`**）；
  第 643–652 行 backend `depends_on: clamav: condition: service_healthy`；worker-notify 同款。
- **触发**：任何 `docker compose up`（新建或重建 backend）。
- **影响**：Compose 在启动依赖阶段直接报
  `dependency failed to start: ... has no healthcheck configured`，**全栈起不来**。
  注意这与「病毒扫描降级」是两件事，报错文本用不上业务线索，排查成本极高。
- **最小修复**（二选一，不要两套都上）：
  1. 给 clamav 加 `healthcheck: test: ["CMD","/usr/local/bin/clamdcheck.sh"]`；
  2. 改 `condition: service_started`，把「扫描不可用」交给上传路径的 `FileErr.SCAN_UNAVAILABLE`
     显式报错（该路径已是 fail-closed）。
- **验证**：`docker image inspect clamav/clamav:stable --format '{{json .Config.Healthcheck}}'`
  ——若官方镜像自带 HEALTHCHECK，本条降级为「语义未固定」；否则按上述修。
- **推翻条件**：镜像自带 HEALTHCHECK，且能证明「clamd 签名加载完成后才转 healthy」。
  当前 `clamav/clamav:stable` 是浮动 tag，该语义未被本仓库固定。

### R2 [blocker] 内部 seam 公网可达

- **位置**：[deploy/apisix/apisix.yaml](../deploy/apisix/apisix.yaml) 第 151–165 行（`auth-prefix`，
  `uri: /api/v1/auth/*`，`priority: 120`，插件仅 `client-control` + `cors`，**无 `ip-restriction` /
  `uri-blocker`**）；[.env.example](../.env.example) 第 183 行 `LKM_AUTH_HTTP_TOKEN=change-me`；
  [docker-compose.yml](../docker-compose.yml) 第 681 行守卫为 `${VAR:?}`（**只拒空、不拒占位符**）。
- **触发**：攻击者知道网关域名，直接 `POST /api/v1/auth/internal/*`。
- **影响**：升权/审计/验密/票据等内部端点暴露为公网 API，唯一保护是单一共享令牌；而运维照抄
  `.env.example` 时该令牌字面就是 `change-me` → 防护强度从「需破解」降到「默认口令」。
- **最小修复**：
  1. 该路由加 `uri-blocker` 拦截 `^/api/v1/auth/internal/`；或把 internal 端点整体迁到
     `/internal/*` 前缀且只走容器网络（若走前者，需与现有 `auth-login:150`、`api-prefix:110`
     一并复核优先级）；
  2. 启动断言拒绝 `change-me` / `changeme` / `placeholder` 等占位值，`.env.example` 留空并写生成命令。
- **验证**：外网 `curl -s -o /dev/null -w '%{http_code}' https://<域名>/api/v1/auth/internal/admin-ids`
  期望 403/404（网关拦）；容器内直连 `http://auth:8001/api/v1/auth/internal/admin-ids`
  期望 401（**缺内部令牌**，说明缝本身仍活着、只是不经公网）；用 `change-me` 启动应 fail-fast 退出。
  端点选真实存在的 `admin-ids` 而不是自造 `/health`：后者 404 无法区分「网关拦住了」与「没这条路由」。
- **推翻条件**：生产 APISIX 实例在仓库外另行插入了白名单插件（仓库内不可见）；或确认 internal
  端点全部自带二次鉴权。

### R3 [blocker] admin → Bot 面板票据无独立授权

- **位置**：`LKM-service/app/modules/admin/bot_router.py` 第 25–40 行
  （`admin_bot_sso_ticket(cur: CurrentUser = require_admin)` 直接
  `mint_bot_sso_ticket(cur.id, cur.account_level)`）。
- **触发**：任一社区 admin 会话被盗或越权取得。
- **影响**：换来一张 60 秒、一次性的 Bot 面板 SSO 票据 → Bot 面板会话。面板侧即 Bot 控制面
  （**静态推断**，本轮未读面板权限模型与插件执行链），最坏情况涉及宿主代码执行。
- **最小修复**：铸票前加独立能力点（不是 `account_level >= admin`，而是 `can_access_bot_panel`
  一类）+ 写审计事件 + 高风险操作二次验证；票据绑定来源 IP/会话指纹。
- **验证**：无该能力点的 admin 调 `POST /api/v1/admin/bot/sso-ticket` 应 403 且留审计记录；
  有该能力点应 200 且票据一次性。
- **推翻条件**：Bot 面板侧对票据做了独立降权映射（需读 `LKM-bot/dashboard` 的 sso 校验）——**未覆盖**。

### R4 [blocker] 无经网关的全栈验收证据

- **位置**：[scripts/demo_golden_path.sh](../scripts/demo_golden_path.sh) 第 30 行
  （`BASE_URL="${BASE_URL:-http://127.0.0.1:8000}"` 直连 backend）；`docs/acceptance/` **目录不存在**
  （脚本自建，说明从未在本工作区跑通并留档）；根 CI 仅
  [.github/workflows/contracts.yml](../.github/workflows/contracts.yml)，无 job 调用它。
- **触发**：任何「一期可交付」的验收动作。
- **影响**：脚本全绿也只证明「backend 进程 + DB + Redis」可用，**完全绕过** APISIX 路由、
  `/lkm/` 预签名改写、CORS、证书、WS upgrade——而这四处恰好是历史出过 502 的地方
  （[OPS-CHEATSHEET.md](./OPS-CHEATSHEET.md) 第 126 行）。且交付日无法回答「上次验收何时、是否通过」。
- **最小修复**：不改代码——`BASE_URL` 指到网关域名跑一次，产物落 `docs/acceptance/`，
  并加一条 CI job（compose up 后跑、归档日志）。
- **验证**：见 §7 用例 A1。
- **推翻条件**：任一环境存在 `docs/acceptance/golden-path-*.log` 且 `BASE_URL` 为域名、无 skip/fail；
  或 CI 有等价 job。

### R5 [blocker/条件] compose 站点身份硬编码

- **位置**：[docker-compose.yml](../docker-compose.yml) 第 711–714 行——`LKM_RP_ID: 124.220.55.235`、
  `LKM_ORIGIN: http://124.220.55.235`、`LKM_GITHUB_REDIRECT_URI`、`LKM_FRONTEND_CALLBACK`
  **四行全是字面量、无插值**；对照第 809 行 auth 容器同一语义键写的是 `${LKM_RP_ID:-...}`。
  k8s 侧有正确 overlay：`deploy/k8s/overlays/prod/site-identity.yaml` 第 13–18 行；compose 侧没有。
- **触发**：一期对外用域名 + TLS（[DEPLOYMENT.md](./DEPLOYMENT.md) 第 1084 行正是这么要求的）。
- **影响**：WebAuthn 的 RP ID 必须是 origin 的可注册域后缀 → 页面在 `https://<域名>` 而 RP ID 是 IP，
  浏览器**直接拒绝**注册/登录；GitHub OAuth 回跳到 `http://IP`；预签名下载在 https 页面被混合内容拦截。
  四类功能静默失效，日志里未必有明显错误。
- **最小修复**：四行改成 `${LKM_RP_ID:-...}` 形式 + 5 个键登记进 `.env.example`（含「换域名必改」注释）
  + 文档改为「改 `.env` 即可」；顺带第 686 行 `LKM_S3_PUBLIC_ENDPOINT_URL` 默认仍是 `http://`，一并处理。
- **验证**：新增 `LKM-service/tests/deploy/test_site_identity_config.py`：解析 compose，断言
  backend/auth 两块这 5 个键的值**必须以 `${` 开头**，且两处默认值相等。
- **推翻条件**：一期明确只在裸 IP + http 交付，且交付合同写明「不得启用域名」——那本条降为「中」。
