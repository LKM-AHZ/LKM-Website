## 一、服务形态与部署拓扑

| 事实 | 代码入口 |
|---|---|
| AUTH 独立进程 | `auth/main.py`：认证、用户资料、挑战/Passkey/OAuth、内部读面、JWKS 与健康检查；独立 auth 库 |
| 业务服务装配 | `main.py → boot/backend.py → boot/assemble.py → app/main.py`；两侧 bootstrap 向 core 注册**模型/任务/端口/错误码**，路由由各模块 `ROUTERS` 汇总后由各自入口挂载 |
| 认证路由归属 | 认证**写面**（`/api/v1/auth/*`、`/api/v1/admin/auth/{login,refresh,logout,2fa}`）只由 `auth.main` 提供；后台登录态读面 `/api/v1/admin/auth/me` 仍在业务单体（网关 `admin-auth-me` 精确路由到 backend），业务侧不挂其余 auth 路由 |
| auth 攻击面 | 除对外认证面外，`auth.main` 另挂 `/auth/internal/*`（内部缝，网关公网拦截）与 bot 面板 SSO（`aud` 由 `LKM_BOT_SSO_AUDIENCE` 决定，默认 `lkm:bot`） |
| 网关分流 | 父仓 `deploy/apisix/apisix.yaml` 把认证与业务请求送到各自进程 |
| 业务模块 | `app/modules/`；装配项由各模块 `manifest.toml` 声明，`app/modules/spec.py` 校验定序后派生 `MODULES` / `ERROR_MODULES` / `APP_MODEL_MODULES` / `APP_TASK_MODULES` |
| 后台进程 | `boot/workers/` 提供进程入口，`core/worker*.py` 提供共享实现；实际服务以父仓 Compose/Kustomize 为准 |
| 基础设施 | 父仓 `docker-compose.yml` 与 `deploy/` 管理数据库、缓存、消息、存储、网关、搜索、可观测性和可选 Bot 等服务 |
| 静态官网 | 已迁出独立仓库与服务器，不在本编排内 |

消息总线由 `LKM_MESSAGE_BUS` 选择：当前 Compose 默认 `rabbitmq`，直接启动后端时
`core.config.Settings` 默认 `pulsar`。切换时还需配置所选 broker 的地址并启动该服务；
不能把某一部署环境的默认值当成两种启动方式的共同默认值。

## 二、技术栈清单（实况）

| 层级             | 实况选型                                                                               | 证据                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Web 框架         | FastAPI + Pydantic v2                                                     | `pyproject.toml`                                                                                  |
| API 风格         | REST `/api/v1` + Strawberry **只读** GraphQL                                         | `app/api/router.py`、`app/api/graphql.py`（显式拦截并拒绝任何 `*Mutation`）                                |
| Passkey          | **WebAuthn**（`webauthn>=2,<3`）+ passkey 登录/因子/凭据管理                              | `auth/router_passkey.py`、`auth/service_passkey.py`、`auth/models.py`                                   |
| ORM / 迁移       | SQLAlchemy 2.0 async + Alembic（**双链**）                                             | `core/db/session.py`；`alembic/`（业务）+ `alembic_auth/`（认证）                                            |
| 数据库            | PostgreSQL + **TimescaleDB 扩展**（hypertable / 压缩 / **连续聚合**；不启用保留策略，扩展缺失则降级为普通表） | `alembic/versions/0001_initial.py`（hypertable 装配已并入基线）、`core/db/init_db.py` 的 TimescaleDB 装配段          |
| 缓存 L2 / 会话 / 锁 | Redis 协议；Compose 默认 Redis 7，可替换 Dragonfly                                          | `core/redis.py`、父仓部署手册                                                                                 |
| 缓存 L1          | **自实现有界 TTL+LRU**（`OrderedDict`，**非 aiocache**）                                    | `core/local_cache.py`                                                                              |
| 消息总线           | Pulsar / RabbitMQ，按 `LKM_MESSAGE_BUS` 选择                                           | `core/bus/`（实现）、`core/messaging.py`（兼容垫片）、`core/config.py`                                      |
| 调度             | **Prefect**（cron deployment + 复杂管道；**无 APScheduler 进程**）                          | `boot/flows_deploy.py`（注册 deployment）、`app/flows/*.py`、`core/scheduler.py`（cron 发布体）、compose `prefect-*` |
| 接入网关           | **APISIX**（standalone、无 etcd）                                                      | `deploy/apisix/{config.yaml,apisix.yaml,render.sh,smoke.sh}`；k8s `deploy/k8s/base/gateway/apisix.yaml` |
| 搜索             | **三引擎并存可选**：PG FTS（默认）/ Meilisearch / OpenSearch                                   | `app/modules/search/engines/{meili,opensearch}.py`、`factory.py`、`settings.search_engine` 默认 `pg`       |
| 文件存储           | Local/S3 双后端；Settings 默认 local，生产 Compose 使用 S3/MinIO                              | `core/storage/{base,s3,local,factory}.py`                                                              |
| 可观察性           | Sentry + Prometheus/Grafana + OTel(Collector) + **SigNoz**(自托管) + ClickHouse(日志分析) | `core/{apm,tracing,metrics,clickhouse}.py`、`deploy/{signoz,otel,grafana,clickhouse,prometheus}/`       |
| 密钥管理           | **Infisical**（universal-auth 启动拉取；无 Vault）                                         | `core/secrets_bootstrap.py`、`deploy/docker-entrypoint.sh`                                              |
| 强制边界           | import-linter（**4 条** forbidden 契约）                                                | `pyproject.toml`                                                                                       |
| 读热路径序列化        | **msgspec**（interaction/feed/files/search/notification 等列表读口），Pydantic 仍负责校验 | `core/wire.py`、`app/modules/*/wire.py`                                                                 |
| 部署             | Compose / Kubernetes：backend、auth 与独立 worker                                       | 父仓 `docker-compose.yml`、`deploy/k8s/`                                                                  |

依赖选型以 `pyproject.toml` 为准；RabbitMQ 适配通过 `aio-pika` 实现。

## 三、数据访问层与数据模型

### 3.1 两库两 Base

| 库                | metadata                     | 位置                 | 内容                         |
| ----------------- | ---------------------------- | -------------------- | ---------------------------- |
| 认证库 `lkm_auth` | `AuthBase` / `auth_metadata` | `auth/db/base.py`    | 见 §3.2 与 ORM 模型             |
| 业务库 `lkm`      | `Base`                       | `core/db/base.py` | 内容/交互/通知/发件箱/宽表等 |

- 业务模型由 `app.bootstrap` 登记到 `core.db.model_registry`；auth 模型由 `auth.bootstrap`
  调用自有注册钩子，使用独立 `AuthBase`。`boot.assemble` 汇总装配，业务 metadata 不含 auth 表。
- **跨 realm 引用是裸 uuid**：业务表的 `author_id` / `owner_id` / `uploader_id` 是 `uuid` 指向 auth realm，
  **跨库无 FK**；主服务**绝不写 auth 表**（跨包身份操作通过 core 端口交给 auth 实现，见 §4.1）。

### 3.3 主键 / 时间戳 / 软删除 / 命名

| 约定     | 实况                                                                                                                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 主键     | **UUID**。PG 原生 `uuid` + 自建 `public.uuid_generate_v7()`（RFC 9562 uuid7，时间有序）。但同一微秒内只差随机位、跨主机依赖时钟同步，故 `order_by(id)` 只是**近似**按时间排序，不能当亚微秒级 keyset 游标；严格全序用 `created_at`。**例外**：`outbox_events.event_id` 保持 `String(36)`——它是 Pulsar Avro-record schema 契约，改类型会击穿事件链路 |
| 时间戳   | `TIMESTAMPTZ`，应用层统一 UTC（`UTCDateTime`）                                                                                                                                                                                                      |
| 软删除   | `SoftDeleteMixin`（`deleted_at`）：content/articles/blog 评论、`user_follows`/`board_follows` 等；评论树级联仅见 article/blog repository 的 recursive CTE（`content_comments` 未见）                                                  |
| 命名约定 | **无全局 `naming_convention`**。索引基本统一 `ix_`；部分 UniqueConstraint/FK 未显式命名，PG 会生成 `<table>_<col>_key/_fkey`，新迁移应显式命名                                                                                                        |
| asyncio  | 全部 `AsyncSession`，驱动 `asyncpg`                                                                                                                                                                                                                 |

### 3.4 Alembic 迁移

- **双链**：业务库使用 `alembic/` + `alembic.ini`，认证库使用 `alembic_auth/` +
  `alembic.auth.ini`。2026-11-21 再次压平后，两条链各只剩一条自包含基线：
  业务 `0001_initial`、认证 `0001_auth_baseline`；考试/项目/关系/订阅/日历/好友等增量
  已折入业务基线，挑战/桌面 OAuth/Tinode 映射已折入 auth 基线。
  版本状态以各链 `alembic heads/history` 的实际输出为准，不能把已有数据库直接重新标记为基线。
- 命名采用 `NNNN_语义名`。业务基线**显式 DDL 建表**；认证基线在迁移内调用
  `auth_metadata.create_all()` 再补既存库列，两条基线都只在空库上等价于「一条自包含基线」。
- 运行期另有 `core/db/init_db.py` 的 `create_all` 通道 + `_sync_additive_schema` 加性同步（给已存在的表补列）。
- **两条权威通道的边界**：`LKM_USE_ALEMBIC=false`（默认，compose 显式下发）走 `create_all`，新库零维护，
  但只支持**加性**变更（加列/加索引）；`true` 走启动期 `alembic upgrade head`。既有库切到迁移链前
  必须先备份、核对并补齐目标结构，再 stamp 对应基线；stamp 只更新版本记录，不修复结构。生产走 create_all 时启动日志会显式 WARNING。
- **漂移门禁**：`scripts/check_schema_drift.py` 在空库上跑两条迁移链（业务 / auth）再跑 `alembic check`，
  比对「迁移建出的结构」与 ORM metadata；CI 的 `test` job 每轮执行，任一差异即红。
  这是「两套权威」不至于分叉的机器保证。
- 大表变更先走 `--sql` 离线评审；加列、回填、建索引及非空收紧已有 `scripts/online_ddl.py` 分阶段工具（默认只输出计划，执行须显式 `--apply`）。

### 3.5 Repository 与连接池

- `core/db/repository.py` `AsyncRepository[ModelT]` 泛型基类：CRUD、动态软删、乐观锁 CAS、**只 flush 不 commit**。
- `core/db/repo.py` 提供模块级事务原语 `get_or_raise` / `consume_once` / `isolated_update`。
- **业务查询走 ORM/Repository**；项目待审唯一索引谓词用 SQLAlchemy 表达式，无裸 SQL 业务查询。
- 分层：14 个模块有独立 `repository.py`（content/comment/columns/qa/blog/feed/files/interaction/
  notification/points/exam/projects/search/rbac）；admin/health/treehole 等按 service 组织。
  部分子域（如 content 的 boards）仍由 service 直查，分层属约定、未被机器强制（见 §8.2）。

**连接池（`core/config.py`、`core/db/session.py`）**：

| 池             | pool_size / max_overflow | 其他                                              |
| -------------- | ------------------------ | ------------------------------------------------- |
| web（API）     | 10 / 20                  | `pool_recycle=1800s`、`pool_timeout=30s`          |
| worker（后台） | 5 / 10                   | 经 `new_worker_session`（`session.py`）独立池 |
| auth           | 10 / 20                  | 由 `auth/db/session.py` 惰性创建                    |

> **仍只有 web / worker / auth 三种池**。调度由 Prefect deployment 承载，不持应用 DB 连接，故未单列调度池。

**服务端超时兜底**：`db_statement_timeout_ms`（默认 30s）与 `db_idle_tx_timeout_ms`（默认 60s）
在建连时随 `server_settings` 下发，挡住「一条慢查询把池位占死」与「事务开着等下游 HTTP」两类
池泄漏——`pool_timeout` 只能让排队者失败，停不下正在跑的语句，两者互补。该设置只作用于 asyncpg
应用连接：启动期 DDL 在事务内 `SET LOCAL statement_timeout = 0` 解除，Alembic 的 psycopg2 连接不受影响。

### 3.6 TimescaleDB

- `outbox_events` / `outbox_archived` 转为 **hypertable**（按 `created_at` 时间分区），`outbox_archived`
  启用**原生压缩**（`add_compression_policy(..., INTERVAL '7 days')`）。**不启用保留策略**：旧部署若曾对
  `outbox_events` 设过按时间 DROP chunk，启动装配会显式 `remove_retention_policy`（热表上可能仍有 pending 事件）。
- `outbox_event_keys` 是普通表，承担跨分区 `event_id` 的**全局唯一/去重**（分区表自身的
  `(event_id, created_at)` 唯一约束无法跨分区生效）。
- 认证库 `audit_logs` 在 `0001_auth_baseline` 中转为 **hypertable**（7 天 chunk；无 Timescale 时 WARNING 跳过）。
- 扩展缺失时（无 Timescale 的 PG）**降级为普通表**并 WARNING，不阻断启动。
- **PG「连续聚合视图」已落地**：`points_ledger`（hypertable）+ `points_daily`（日桶 × `reason`
  即行为类型）。**cagg 只在应用启动期**由 `core/db/init_db.py::_ensure_continuous_aggregates` 装配
  （自开 AUTOCOMMIT；`CREATE MATERIALIZED VIEW ... continuous` 不能在事务块内执行）。create_all 与
  alembic 两条启动通道共用该函数，**迁移本身只建 `points_ledger` hypertable、不建 cagg**。
  唯一读口 `/admin/points-report`（离线面，非 TimescaleDB 实例返 503）。当前只登记 `points_daily`
  一个 cagg，内容/用户增长类指标不在覆盖内。

## 四、认证、鉴权与安全（AUTH 微服务）

### 4.1 边界与公开面

- `auth/` 独立拥有认证路由、服务、模型、JWT 与身份读缝。
- app 只依赖 `core.contracts` 和 `core.ports`（如 `authz`、`snapshot`、`users`、`verify_keys`），
  不直接导入 auth。auth 同样不导入 app；共享存储与流程纯体层位于 core。
- `auth.ports_impl` 提供端口实现，`auth.bootstrap` 登记到 core；业务侧的
  `app.bootstrap` 登记业务模型、任务与自有端口实现。`boot.assemble` 是汇总两侧的组合根，
  最后通过 `core.ports.validate_all()` 检查必需端口是否齐备。
- 独立 AUTH 入口 `auth.main` 自行装配自有路由与生命周期，不加载业务 REST/GraphQL/WS。
- **双形态已退役（2026-11-13）**：单体不再挂载 auth 路由，`/api/v1/auth/*` 与
  `/api/v1/admin/auth/*` 只由独立 AUTH 进程提供，**例外**是后台登录态读面
  `/api/v1/admin/auth/me`（精确路由 `admin-auth-me` → backend，见 §一）。随之删除：
  - `auth/bootstrap.register()` 不再向 `core.route_registry` 登记 `auth.ROUTERS`；
  - app 侧鉴权恒经 HTTP 缝（`core.ports.authz` 不再取 `authz_session`，`REQUIRED_PORTS`
    移除该端口），不再有“缝关闭 → 本地读 auth 库”的兼容分支；
  - snapshot 热点读、审计写、准入/升权、admin 会话均恒走 auth internal HTTP；
  - 生产配置强制要求 `LKM_AUTH_HTTP_URL` + `LKM_AUTH_HTTP_TOKEN`；`/health` 与 `/readiness`
    把 auth 视为硬依赖（无 disabled 形态）；
  - passkey 挑战清理由 `auth.main` 独占，主进程不再起该 task；
  - 本地开发 `dev.sh` / `dev.ps1` 同时启动 backend 与 `python -m auth.main`，并注入内部缝地址/令牌。

  **例外（只读直连）**：后台用户列表/统计（`/admin/users`、`/admin/stats`）在 backend 进程内开
  auth 库**只读**会话（`core.ports.audit.new_auth_session` + `auth.snapshot`），不跨库写。
  因此 backend 部署必须注入 `LKM_AUTH_DB_*`：Compose 的 `backend` 服务与 k8s 的
  `lkm-config-authdb` 均已配置（密码随 `lkm-secrets` 下发）。

  `app.main` 构建期的 duplicate operationId 警告随之消失。

### 4.2 JWT + Refresh Token

| 项            | 实况                                                                                                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 签名算法      | **RS256-only**：`encode` 用 RSA 私钥签（缺私钥即 `RuntimeError`），`decode` 只放行头部 `alg=RS256`、其余一律拒（`auth/jwt_keys.py`）。HS256 对称兼容与 `jwt_hs_fallback` 灰度开关已移除 |
| 密钥          | `LKM_JWT_PRIVATE_KEY(_FILE)` / `LKM_JWT_PUBLIC_KEY(_FILE)`；签发方(auth)持私钥，验签方持公钥（无密钥由 readiness 报「验签不可用」）。`LKM_JWT_SECRET` 契约已删除                        |
| 有效期        | access 与 admin cookie 默认 15min；refresh 默认 7 天，轮换保留初次到期时间（`core/config.py`）                                                                                                              |
| 轮换          | `refresh_access_token` 用 `consume_once` 原子撤销旧 token 再发新对；DB 只存 SHA-256 哈希（`auth/service_auth.py`）                                                        |
| JWKS          | `/.well-known/jwks.json`（`auth/router_jwks.py`），RFC7638 `kid`                                                                                                                  |
| 验签公钥就绪  | `verification_status()`（`jwt_keys.py`）+ 运行期 JWKS 拉取（`:231-295`）；readiness 有 `verify_key` 硬依赖项                                                                     |
| audience 隔离 | `lkm:web` / `lkm:temp` / `lkm:admin` / `lkm:bot`（`auth/security.py`、`core/ports/authz.py`、bot SSO 的 `LKM_BOT_SSO_AUDIENCE`，默认 `lkm:bot`）                                  |
| 算法混淆防护  | `decode` 只接受头部 `alg=RS256`，其余算法直接拒绝（无分支回退）                                                                                                                          |

### 4.3 密码与会话安全

- 口令哈希：`argon2.PasswordHasher`（Argon2id），内建 salt；用**虚拟哈希**防用户名枚举（`auth/security.py`）。
- 会话：refresh token 落 DB `refresh_tokens`（权威）；撤销预检走 Redis。
- **撤销**：`token_version`（DB 比对）+ `jti:block:{jti}` / `tv:min:{user_id}` 预检缓存
  （`auth/token_revocation.py`，TTL 带抖动），**缓存只用于加速拒绝、绝不据此放行**，DB/seam 为最终判据。
- 多设备撤销 `revoke_all_refresh_tokens`（`auth/service_auth.py`）；admin 登出按 jti 即时失效。
- 登录限流 + 失败锁定（`auth/limits.py`、`locked_until`/`failed_login_attempts`）。
- 管理员 cookie 使用 `samesite="lax"`，生产启用 Secure；前台 refresh 由客户端管理，不落 HttpOnly cookie。SameSite 是 cookie 策略，不等同于独立 CSRF token 校验。

### 4.4 RBAC 权限模型

- 业务权限入口位于 `app/modules/rbac/`；共享角色层级、约束和契约位于 core，
  auth 负责身份、角色分配与会话激活裁决。
- `role_permissions` 保存业务侧权限映射；认证库 `user_roles` 保存附加角色，
  `profiles.role` 与账号等级仍参与兼容角色派生。
- 支持角色继承、静态职责分离（SSD）与会话动态职责分离（DSD）；层级配置见
  `core/rbac_roles.py`，设置见 `core/config.py`。
- 鉴权依赖经 `core.ports.authz` 取得当前用户，业务权限判定经 `require_permission` 等入口。
  完整配置和会话激活规则见 [后端 README](../LKM-service/README.md#rbac0--rbac1--rbac2--rbac3-角色与权限)。

### 4.5 中间件与防护

`install_security_middleware`（`core/middleware.py`）装配 **4 件**：

1. **TrustedHost**（生产禁 `*`）。
2. **CORS**——**仅非生产**在应用层挂；生产 CORS 权威在 APISIX。
3. **SecurityHeaders**：`nosniff`、CSP `frame-ancestors 'none'`、`X-Frame-Options: DENY`、Referrer-Policy、
   Permissions-Policy；HSTS **仅生产**。
4. **RequestId**：写 ContextVar + 回写 `X-Request-ID` + 进 JSON 日志。

**顺序**：`add_middleware` 装配序为 TrustedHost → CORS → RequestId → SecurityHeaders；请求执行序由外到内
相反（SecurityHeaders 最先、TrustedHost 最后）。

另：`GraphQLHTTPMiddleware`（硬超时，见 §6）。**无全局限流中间件**——限流在 APISIX + 端点级 `check_code_rate_limit`。

### 4.6 密钥管理

- **Infisical** 已接入：`core/secrets_bootstrap.py`（universal-auth machine identity，支持 `_FILE` 引导），
  `deploy/docker-entrypoint.sh` 启动前拉取。**Vault 不存在**。
- **口径**：**既有环境变量优先，Infisical 只补缺**；未启用时 fail-open 回落 `.env`。故非"零明文"终点。

### 4.7 因子挑战、Passkey 与 OAuth

- **挑战-因子轮转登录**（`auth/challenge.py`、`auth/router_challenge.py`）：`POST /auth/challenge`
  （账号 + `X-Device-Id`，**不查账号是否存在**）、`GET /auth/challenge/{id}`、`POST /{id}/factor`
  （`password`/`code`/`totp`）、`POST /{id}/request`（重发验证码）、`POST /{id}/cancel`、
  `POST /{id}/passkey/start|complete`。状态存 `auth_challenges`：`steps_left[0]` 是下一步、
  `steps_done`、`attempts ≤ 5`、TTL 5 分钟、`status=pending|complete|cancelled`、绑定
  `device_hash`（**不绑 IP**，桌面换网不失效）。首因子 API 目前仅接受 `password|code`；
  引擎已登记 `passkey` 首因子，但请求 schema 尚未放行。管理员首次强制 TOTP 返回
  `setup_required` 并消费当前挑战。
- **Passkey / WebAuthn**（`auth/router_passkey.py`、`auth/service_passkey.py`）：
  `POST /auth/passkey/register/{begin,complete}`（需 normal 等级）、
  `POST /auth/passkey/login/{begin,complete}`（公开）、`GET /auth/passkey/credentials`、
  `DELETE /auth/passkey/{cred_id}`（需 2FA）；表 `passkey_credentials` / `passkey_challenges`；
  RP/origin 由 `LKM_RP_ID` 等配置；挑战清理由 `auth.main` 独占。
- **GitHub OAuth 桌面回跳**（`auth/router_oauth.py`、`auth/service_oauth.py`）：
  `GET /auth/oauth/github/login?redirect_uri=&challenge=` 与绑定路由；回调对 loopback 重定向
  一次性 code，`POST /auth/oauth/desktop/exchange` 以 PKCE verifier 兑换会话；一次性码落
  `oauth_desktop_codes`。
- **设备标识**：挑战与 Passkey start/complete 端点必填 `X-Device-Id`（≤128 字符，
  `auth/deps.require_device_id`）；挑战只存 `sha256` 哈希，不存原始设备 id。

## 五、消息驱动：统一消息入口与 Pulsar 拓扑

### 5.0 抽象层与命名空间

- 实现位于 `core/bus/`：`runtime.py`（publish/连接生命周期）、`consumer.py`（
  `run_subscription`/ack）、`topics.py`（routing key 与订阅注册表）。`core/messaging.py` 是
  **兼容垫片**（只 re-export 历史导入路径，禁止新增逻辑）。
- 业务按 `routing_key` 发布，订阅名走 `SUBSCRIPTIONS` 注册表（**拿不到直接指名 topic 的入口**）。
- **命名空间白名单** `NAMESPACES = {auth, biz, system}`；`_topic()` 对未知命名空间 import 期即抛错。
- import 期校验两条：订阅声明的 routing_key 必须与其 **topic 同命名空间**，且 routing_key 的 topic
  必须**等于**该订阅的 topic（`core/bus/topics.py`）——隔离由消息层强制。
- Pulsar 路径使用上述 topic；RabbitMQ 适配在 `core/bus/transports/rabbitmq.py`，复用 routing key、
  订阅和 handler。传输选择统一在 `core/bus/runtime.py`，业务不直接调用 broker 客户端。

### 5.1 事务发件箱

| 组件        | 实况                                                                                                                                                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 入队        | `core/db/outbox.py` `enqueue_outbox`（同事务入队）；`event_id` 的**跨分区全局去重**由普通表 `outbox_event_keys` 的 `INSERT ... ON CONFLICT` 保证，分区表上仍保留 `(event_id, created_at)` 唯一约束；显式传入 id 时另查热/归档表 |
| relay       | `core/outbox_relay.py` `relay_poll`：`FOR UPDATE SKIP LOCKED` 领取、认领即写锁并 commit；陈旧锁阈值取 `max(outbox_lock_ttl_s, pulsar_operation_timeout_s + 10)` 重领                                                |
| leader 选举 | **Redis 租约**（`SET NX EX` + 原子续约），`worker_outbox` 为入口；指标 `outbox_leader_total{acquired,contended,renew_failed,stale_reclaimed}`、`outbox_pending_count`                                                                |
| 重试        | `MAX_TRIES=5`，指数退避 cap 1h；达上限**直接删 outbox 行并迁 `event_failures`**（outbox **无 `status=failed` 行**）。**确定性永久失败**（事件契约违约等）首次投递即折叠进 `event_failures`，`attempt_count` 可为 0 |
| 归档        | `archive_published` 先写 `outbox_archived` 再删                                                                                                                                                                                      |
| 人工重放    | `core/db/event_failure.py` 的 `replay_failure` + `app/modules/admin/event_failure_router.py`：`GET /admin/event-failures`、`POST /{id}/replay`（**沿用原 event_id 重入 outbox**，走发件箱而非直投；成功后标记 replayed_at，保留原失败记录供审计；总线未启用时返 503） |
| 幂等        | `core/db/event_processed.py`（`scope,event_id` 复合主键）+ `worker.py:_dispatch_with_dedup`；dispatch 在**事务级 advisory lock** 下串行，非纯 best-effort                                                                              |

### 5.4 跨 AUTH 读模型

- **在线读 = `user:snap` 缓存 + AUTH 只读 API 回退**：
  - `core/user_cache.py`：`user:snap:{id}` 键，L1+L2 两级，**版本 CAS**（`sv`）防 LWW，**epoch 墓碑**防复活，

  - AUTH 只读面：`auth/snapshot.py`（读路径）、`auth/user_http.py`（进程内 HTTP）、
    AUTH 端点 `GET /api/v1/auth/internal/users/by-ids`（`auth/router_read.py`，批量、分块、
    单次上限 `BATCH_IDS_MAX=200`）。
- **变更即失效**：AUTH 发 `user.updated`/`banned`/`session_revoke` → 主服务消费**仅失效 `user:snap`**
  （`auth/tasks.py` `invalidate_user_snap`，注册点在 `:259`），**不写缓存值**；跨实例 L1 失效经
  `core/user_cache_events.py` 的 `cache:l1:invalidate` 广播（**只删 L1，不 DEL L2**）。
- **`user_dim` 报表宽表**：`core/db/user_dim.py` 表 + `app/flows/user_dim.py`（Prefect flow：增量/ids 回填/对账）
  - `auth/user_dim_sync.py`；**只读副本、只服务运营报表/后台列表**，在线读绝不读它。
    `auth/tasks.py` 在 `user.*` 失效路径上**同时** `refresh_user_dim_event`——**已回审并保留**（Profile-only
    变更不 bump `users.updated_at`，纯周期谓词看不见它；且为幂等 upsert 而非失效）。
- **种子数据**：demo 用户经 `auth/seams.ensure_demo_user`（auth 库会话 upsert 的不可登录用户）创建，
  业务侧只取回裸 uuid——业务库路径**不出现任何 auth 表写**。

### 5.6 缓存策略

- **L1**（`local_cache.py`，有界 TTL+LRU，仅加速）+ **L2**（Redis）。
- `core/cache.py`：`jitter_ttl()` TTL 随机扰动（**L1 只向下扰动**；`jti:block`/`tv:min` 等"TTL 是上界"
  的预检缓存亦纳入）、`cached_read()` singleflight + L2 锁 double-check。
- `core/cache_lock.py`（L2 互斥锁）、`core/singleflight.py`（引用计数回收）。
- **布隆过滤器（`user:snap` id 白名单）**：位图 = 全部合法 user id，落 **Redis bitmap**（跨进程可见）。
  `bloom.definitely_absent(key)` 为真 ⇒ 该 id 从未存在 ⇒ 短路，不打上游。拦截点分两类：
  单值 `user_cache.read_snap_state`/`read_snaps_state` 在 **L2 miss 分支**查；
  `auth/snapshot.py::_retrieve_fields_batch` 在**缓存读之前**先查 `definitely_absent_many`
  （批量入口无法等 miss，故前置）。
  - 完整性靠三处：**全量预热**（`auth/bloom_seed.backfill_user_ids`，cron 每日 03:50 + auth 进程启动后台跑）、
    **建号即 add**（`auth.service_auth.create_user_with_profile` 等）、**只增不重建**（布隆不可删，但已删
    用户的 id 留位图里无害——会落回真实查找由负值缓存兜）。
  - **门禁**：只有 `mark_seeded()` 打过「已预热」标记（带 TTL）才允许拒绝；未预热/标记过期/Redis 不可用/
    命令异常一律**不拦**（fail-open）。`write_negative` **不再**写布隆（那是反语义）。
  - 覆盖场景：客户端可控 key 的读路径，如 `POST /api/v1/users/{user_id}/follow` 传任意 uuid。
- 计数：写路径与明细**同事务改计数列**（写穿，`LKM_COUNTERS_WRITE_THROUGH` 默认 true）；Redis write-behind
  退为回退通道；对账按 `counts_reconciled_at IS NULL` 增量扫 + 日级全量兜底 `reconcile_content_counts_full`(04:00)，
  震荡只告警不自动暂停。

### 5.7 WebSocket

- `app/ws/{broker,manager,router}.py`，对外路由 `/api/v1/ws/events`；基于 L2 pub/sub（`ws:*` psubscribe），
  频道白名单 `upload` / `notify`（`app/ws/broker.py` 的 `CHANNELS`），`ConnectionManager` 按
  `user→channel`，heartbeat ping/pong + refresh token。
- 事件按 `event` 字段识别，通知中的 `type` 是业务类型；版本由发布方提供，不是全通道序列。格式、心跳和 REST 补偿见 [实时协议](./实时协议.md)。

| 顶级字段串行化 | `GraphQLGuard` 每请求一把 `asyncio.Lock`，仅对顶级字段加锁（共享 `AsyncSession` 不允许并发）                                                                                                      |

## 七、工程实践

### 7.1 错误处理协定

- 统一信封 `ApiResp{code, message, data, request_id}`（`core/common.py`）——字段是 **`message`**
  ；客户端读取约定见 `LKM-desktop/lib/core/api/api_client.dart`，`request_id` 与 `X-Request-ID`、结构化日志同源。
- 异常基类 `BizError`（`core/err.py`）+ `CommonErr`/`AuthErr`；错误码 `ns<<16|local` 命名空间编码。
- 唯一冲突统一 **409**（`EMAIL_TAKEN`/`DUPLICATE_LIKE`…；中性兜底 `CommonErr.CONFLICT`），非 400。
- git smart-HTTP、`/auth/internal/*`、bot-sso 全走统一 handler（`BizError` 可携带响应头，
  git 的 `WWW-Authenticate` 原样保留）。
- **已知例外**：`app/modules/admin/bot_admin_router.py` 部分路径使用 `raise HTTPException`
  （502/503），响应走 Starlette 默认 `{"detail": …}`，不套 `ApiResp`（待收口）。
- 422 由 `RequestValidationError` 映射；统一 `respond` 路径下 429/503 自动补 `Retry-After`；
  永久失败入 `event_failures`。

### 7.2 可观察性

| 维度       | 实况                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 指标       | `core/metrics.py` + `prometheus-fastapi-instrumentator`；`/metrics` **仅 backend 进程对外暴露**（auth 进程刻意不挂）。worker/auth 进程的业务指标经 **`core/metrics_relay.py` 的 Redis 快照**由 backend 进程聚合代报（见下）                                                                                                                                                                                                                                                                                                                                                   |
| 业务指标   | **API 进程直接暴露**：`post_created_total`、`search_engine_fallback_total`、`pulsar_subscription_backlog`（API 代报）、`graphql_query_{duration_seconds,rejected_total,depth}`、`metrics_relay_{up,instances}`、`db_pool_connections`。**经中继（`RELAYED` 10 项）**：`outbox_pending_count`、`outbox_leader_total`、`notify_failed_total`、`user_snap_cache_total`、`user_snap_singleflight_total`、`cache_lock_total`、`content_index_events_total`、`counts_reconcile_repeated_total`、`audit_events_total`、`event_contract_violations_total` |
| 跨进程取数 | `metrics_relay`：非 API 进程按 `metrics_relay_interval_s`（默认 15s，对齐抓取间隔）把本进程指标快照写进 `lkm:{env}:metrics:relay\|{实例}`（TTL=3×周期，进程没了键自然过期），backend 进程扫描该前缀后聚合——**counter 记远端增量**（远端回退只重置基线、绝不让本地计数回退：既避开 `Counter.inc(负数)`，也让 Prometheus 侧不出现 counter reset）、**gauge 取跨实例 max**（非 leader 副本的 0/陈旧值不得拉低积压读数）。取舍：远端 counter 是「本地 + 增量」的近似，**斜率正确但不适合当绝对总量做账**；gauge 取 max 只对「越大越坏」的量成立 |
| 抓取与告警 | `deploy/prometheus/prometheus.yml` **只抓 `backend:8000`**；规则 **5 文件**（`lkm-outbox`/`lkm-audit`/`lkm-pool`/`lkm-metrics-relay`/`lkm-event-contract`），k8s `kustomization.yaml` 逐条列全（防回归测试 `tests/deploy/test_prometheus_config.py`）。`lkm-metrics-relay.yml` 守的是**中继链路自身**（`metrics_relay_up == 0` 持续 10 分钟即告警），免得"指标静默冻结在旧值"再把假保护挪一层                                                                                                                                                                                                                    |
| 错误追踪   | Sentry（`core/apm.py`，空 DSN 关闭）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 链路       | OTel（`core/tracing.py`，`LKM_OTEL_ENABLED` 默认 false）+ Collector + SigNoz 自托管（compose/k8s）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 日志       | 标准库 logging：`JsonFormatter`（含 `trace_id`/`span_id`/`request_id`）+ `DevConsoleFormatter`（仅 `env=dev` 彩色）；`log_exceptions` 装饰器。ClickHouse 三表：`vector` 只写 `app_logs`；`event_failures`/`audit_logs` 由应用 analytics flow 导出（`profile=clickhouse` 默认关）                                                                                                                                                                                                                                       |
| 运营日报   | `app/flows/ops_daily.py`（cron 每日 03:40）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### 7.3 文件与媒体存储

- `core/storage/`：抽象协议（`base.py`）+ S3 实现（boto3）+ local + factory；endpoint/密钥/region/

### 7.4 部署与工程化

- Dockerfile 多阶段；运行时 `uvicorn --workers ${LKM_WEB_WORKERS}`（**未用 gunicorn**）。
  **非 root 运行**（uid 10001）。容器**未强制只读根文件系统**：Compose/k8s 均未设
  `read_only`/`readOnlyRootFilesystem`，可写位置为 `/data`、`/tmp` 及挂载卷。
- 文档转换子进程另有 RLIMIT：CPU 60s、写文件上限、不产 core；**刻意不设 `RLIMIT_AS`**
  （LibreOffice 会映射远大于常驻内存的虚拟地址空间，2GB 上限会让 docx→pdf 直接失败），
  内存兜底交给 compose 的 `mem_limit`、k8s 的 requests/limits。
- k8s 探针：backend 打 `/api/v1/{liveness,readiness}`，auth 打 `/liveness`、`/readiness`；
  均为 `exec` + urllib（`httpGet` 的 Host 是 Pod IP，会被 TrustedHost 判 400）。backend/auth
  都是 startup + readiness + liveness 三级；**worker 无探针**（`workers.yaml` 明示）。
- CI（`.github/workflows/ci.yml`）job：`lint`（ruff + import-linter + 裸 SQL 检查）、`typecheck`（ty，**阻断**；
  `tests/` 走棘轮 `scripts/check_type_debt.py`，只禁止新增诊断，基线在 `tests/type_debt_baseline.txt`）、
  `migrations`（离线双向 SQL）、`test`（pytest + 真 PG + **schema 漂移** + **覆盖率门槛 80%**，
  当前值以 CI 产物为准）、`integration`（Testcontainers PG/Redis/Pulsar）、`image`（构建不推）、
  `deploy`（仅默认分支的 `workflow_dispatch`：推不可变 SHA 镜像，再调用
  `scripts/deploy_k8s.sh` 对一组固定 Deployment 执行 `kubectl set image` + `rollout status`；
  脚本先校验目标集再改动，避免半套更新）。
- **HTTP 契约快照**：`scripts/dump_openapi.py` 把 `app.openapi()` 渲染成确定性 JSON 存到
  `tests/contracts/openapi.json`，`tests/test_openapi_snapshot.py` 在每轮 pytest 中断言一致。
  客户端接口类型需要与后端契约保持一致，靠这道门禁让字段变更在 review 中可见
  （改接口后跑 `python scripts/dump_openapi.py` 更新快照）。生产环境不暴露 `/docs`、`/redoc`。
- 测试：pytest + xdist（`-n` 按需启用；`addopts` 默认只排除 integration）+ hypothesis 属性测试
  （`tests/test_outbox_props.py`、`test_user_dim_props.py`）；
  事件契约完备性（`tests/test_event_contract.py`：handler 注册表 ↔ 契约登记表 ↔ routing_key 表三者互覆盖）。
  本地没有可用 PG 时，`tests/_pg_bootstrap.py` 会用一次性 docker 实例（`postgres:16-alpine`）兜底，
  地址自动指过去；CI 已有 service 容器，不会触发。`LKM_TEST_PG_AUTOSTART=0` 可关闭。
- **事件契约校验（两层，缺一不可）**：
  - **broker 层**：Pulsar 初始化脚本开启并回读 namespace schema 校验策略。
    该策略不替代业务 payload 校验；RabbitMQ 路径同样依赖应用契约。
  - **应用层**（唯一能真正强制的一层）：`core/event_contract.py` 的 `EVENT_CONTRACTS` 按
    「`fn` → 实参形状（线上 JSON 形态）+ 允许承载它的 routing_key」声明，三处校验：**装配期**
    （`register_task`/`register_cron_job` 校验 handler 形参元数与订阅承载能力，写错在进程启动时即炸）、
    **发布期**（`messaging.publish` 全仓唯一咽喉：违约不发、计 `event_contract_violations_total{fn,side}`
    并写 ERROR 日志；`permanent_failure_reason` 同步判为永久失败，relay 一次折叠进 `event_failures`
    而非重试 5 次）、**消费期**（`worker._on_payload` 违约抛错，进入重投及死信处理）。
    判据取**线上形态**而非 Python 标注（`uuid.UUID` 过 JSON 即 str）；handler 侧只校验**元数**——
    同一 `fn` 的多个 handler（如 `apply_point_event` 四订阅扇出）形参名本就不一致，dispatch 是
    `handler(*args)` 按位置展开。告警见 `deploy/prometheus/rules/lkm-event-contract.yml`。

对象存储抽象在 `core/storage/`，不属于 `app/modules/`。

装配项的单一事实源是各模块的 `manifest.toml`（`name` / `module` / `errors` / `models` / `tasks` /
`aggregate` / `provides` / `requires` / `migrations` / `graphql_versions` / `config`）。`app/modules/spec.py`
收集内置清单与 `lkm.plugins` 入口点提供的外部插件：**内置模块由目录名推导、清单不得写 `module`**；
外部插件必须写 `module`，入口点名须等于 `manifest.name`，入口点须零参可调用，module 可导入且禁止导入
`app`/`auth`/`boot`/`core`。校验分工：`core/plugins/host.py` 管重名、能力归属唯一、`requires` 闭包与成环
及插件加载/定序；`app/modules/spec.py` 管资源路径归属、跨清单重复声明与内置清单约束。按依赖定序后派生
`MODULES` / `ERROR_MODULES` / `APP_MODEL_MODULES` / `APP_TASK_MODULES` / `GRAPHQL_VERSIONS` /
`MIGRATION_DIRS`（另有 `SPECS`/`MODULE_PATHS`）。新增业务域 = 新建目录 + 写一份清单，不改注册表；
清单写错（未知字段、空路径、重复项、越界命名空间、非 `aggregate` 模块声明 `graphql_versions`）一律装配期
失败，而不是运行时 404。`LKM_PLUGIN_DENYLIST` 可在入口点 `load()` 前禁用**外部插件**；内置模块不可禁用，
若把内置名写进名单会直接装配失败。REST 出口见 `app/api/router.py`，GraphQL 见 `app/api/graphql.py`；
auth 自有注册由 `auth.bootstrap` 完成。

### 8.2 依赖方向与门禁

- import-linter **4 条 forbidden 契约**（`pyproject.toml:157-186`）：
  ① `core` 不依赖 `app` / `auth` / `boot`；② `app` 不依赖 `auth` / `boot`；
  ③ `auth` 不依赖 `app` / `boot`；④ 业务模块间不任意依赖。第 4 条的 `ignore_imports` **当前为空**
  （无显式白名单），契约源也不含 `rbac`/`health`。跨模块共享走 `core.ports` 与 `app/contracts/`
  （content/comment/feed/search 的共享 DTO），不靠模块互 import。
- **没有 `layers` 类契约强制 `api → service → repository → db`**——分层是约定，未机器强制。
- 门禁命令：`uv run lint-imports`（CI 阻断）。
- 树洞同样受模块间依赖契约约束；匿名举报经 `core.ports.reports` 端口写入后台审核模型
  （`app/modules/treehole/services/reports.py`），其余业务跨域依赖不得绕过门禁。

### 8.4 插件扩展点（内置模块与外部插件同一套）
